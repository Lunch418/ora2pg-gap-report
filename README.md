# ora2pg-gap-report

Инструмент для оценки миграции Oracle → PostgreSQL Pro (Standard/Certified) **до** её начала.

## Проблема

При миграции с Oracle на Postgres Pro в сегменте Standard/Certified (то есть без
лицензии на Postgres Pro Enterprise и без проприетарной утилиты `ora2pgpro`)
единственный доступный автоматический конвертер — открытый
[`ora2pg`](https://github.com/darold/ora2pg). По независимым оценкам он закрывает
в среднем ~80% задачи перевода PL/SQL → PL/pgSQL. Оставшиеся ~20% (пакеты,
автономные транзакции, `CONNECT BY`, вызовы `DBMS_*`/`UTL_*`, составные триггеры)
сейчас разбираются вручную и, как правило, обнаруживаются постфактум — когда
что-то уже сломалось в проде.

## Что делает этот инструмент

Сканирует схему Oracle **до** миграции и говорит: какие конкретно объекты
`ora2pg` не перенесёт или перенесёт некорректно, почему, и какая примерная
трудоёмкость доработки их вручную. Не замена `ora2pg` — надстройка над ним:
запускает его `SHOW_REPORT` и дополняет тем, что тот явно не показывает.

## Статус

Ранняя стадия. Сейчас идёт валидация предпосылки проекта — сверка того, что
`ora2pg SHOW_REPORT` уже показывает "из коробки", с заявленным списком проблемных
конструкций, прежде чем проектировать детекторы поверх него. См. `docs/research/`.

## Архитектура (черновая, будет уточняться по ходу шага 0)

Приоритет — офлайн-режим: анализ дампа DDL (`DBMS_METADATA.GET_DDL` / `expdp`),
а не обязательное живое подключение к боевой Oracle-схеме. Это принципиально для
целевой аудитории — закрытые контуры, air-gapped среды, госсектор.

```
src/
├── oracle_connector.py      # выгрузка метаданных: офлайн (DDL-дамп) + live-режим
├── detectors/
│   ├── packages.py
│   ├── autonomous_tx.py
│   ├── connect_by.py
│   ├── dbms_utl_calls.py
│   └── compound_triggers.py
├── ora2pg_wrapper.py        # запуск ora2pg SHOW_REPORT, парсинг вывода
├── effort_estimator.py
└── report_generator.py
tests/
docs/research/               # валидация предпосылок, сверка с SHOW_REPORT
```
