# End-to-end example: SCAN → migrate → VERIFY

One real, reproducible walk through the whole lifecycle this tool is built
around — not a synthetic demo, an actual `ora2pg 25.0` run and an actual
`PostgreSQL 16` server, on one small package built around a single
documented gap ([GAP-003](../../docs/research/gap-003-bulk-collect-forall.md),
`BULK COLLECT`/`FORALL`/a local nested-table `TYPE`).

```
./run_demo.sh
```

runs it end to end. What follows is what that script does and why, one step
at a time.

## 1. Scan the Oracle source, gate on it

```sh
ora2pg-gap-report oracle/ --fail-on high
```

[`oracle/bulk_test_pkg.sql`](oracle/bulk_test_pkg.sql) is the exact minimal
example from GAP-003's own research doc: a procedure that bulk-deletes
closed orders using `BULK COLLECT INTO` / `FORALL` and a locally declared
collection `TYPE`. The scan finds all three constructs at `high` severity,
and `--fail-on high` exits `1` — this is the gate a CI pipeline would act
on *before* migration, the same way [`docs/ci-integration.md`](../../docs/ci-integration.md)
describes.

`baseline.json` in this directory is what `--save baseline.json` produced
from this same scan — committed here rather than regenerated by the script,
so the rest of this walkthrough has something stable to compare against.

## 2. Migrate, then VERIFY the *generated* output

[`generated/bulk_test_pkg.sql`](generated/bulk_test_pkg.sql) is real
`ora2pg -t PACKAGE` output (version 25.0, header comment included, not
hand-edited) run against `oracle/bulk_test_pkg.sql`. It compiles cleanly —
`CREATE PROCEDURE` never errors, because ora2pg disables
`check_function_bodies` in its output — but the Oracle-only syntax
(`TYPE ... IS TABLE OF`, `BULK COLLECT INTO STRICT`, `FORALL`) is copied
through completely unconverted, exactly as GAP-003's research doc
describes.

```sh
ora2pg-gap-report --verify --baseline baseline.json generated/
```

reports `STILL_PRESENT` for `bulk_collect`: the same construct the
pre-migration scan flagged is still there in what ora2pg actually
generated. `--verify` doesn't touch a database — this is a static
re-scan of the generated code with the same detectors, compared against
the baseline at detector granularity (see
[`docs/verification-capability-matrix.md`](../../docs/verification-capability-matrix.md)
for why detector-level, not finding-level, is what survives the
Oracle-to-PostgreSQL boundary).

## 3. Fix it for real, VERIFY again

[`generated_fixed/bulk_test_pkg.sql`](generated_fixed/bulk_test_pkg.sql) is
the same procedure, manually rewritten using a native PostgreSQL array and
a `FOREACH` loop — the fix GAP-003's own research doc recommends, not a new
idiom invented for this example.

```sh
ora2pg-gap-report --verify --baseline baseline.json generated_fixed/
```

now reports `NOT_DETECTED`: the flagged pattern is gone. Both the broken
and the fixed procedure were also confirmed against a real local
PostgreSQL 16 server (not just parsed) — the broken one creates cleanly
and fails only at the first real `CALL`, on exactly the line GAP-003's
research doc says it will:

```sh
createdb e2e_demo
psql -d e2e_demo -c "CREATE TABLE orders (order_id bigint primary key, status text);"
psql -d e2e_demo -f generated/bulk_test_pkg.sql        # CREATE PROCEDURE succeeds
psql -d e2e_demo -c "CALL bulk_test_pkg_archive_old_orders();"   # fails here
psql -d e2e_demo -f generated_fixed/bulk_test_pkg.sql  # CREATE PROCEDURE succeeds
psql -d e2e_demo -c "INSERT INTO orders VALUES (1,'CLOSED'),(2,'OPEN'),(3,'CLOSED');"
psql -d e2e_demo -c "CALL bulk_test_pkg_archive_old_orders();"   # succeeds
psql -d e2e_demo -c "SELECT * FROM orders;"             # only order 2 (OPEN) remains
```

## Why there's no single PASS/FAIL at the end

Deliberately: `--verify` reports `STILL_PRESENT` / `NOT_DETECTED` /
`NOT_VERIFIABLE` per detector, not a migration-wide pass/fail. `NOT_DETECTED`
means the pattern wasn't found in the checked code — not "provably fixed"
(a detector could miss a differently-shaped rewrite of the same underlying
bug). Collapsing that into a single gate would be exactly the kind of false
confidence this project's whole `NOT_VERIFIABLE` status already exists to
avoid — see [`docs/ARCHITECTURE.md`](../../docs/ARCHITECTURE.md). The gate
that actually exists and that CI acts on is the *pre-migration* one from
step 1 (`--fail-on`); `--verify`'s job is to hand a human (or a PR
description) an honest, re-checkable answer, not a rubber stamp.
