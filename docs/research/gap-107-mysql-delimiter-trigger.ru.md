# GAP-107: триггер, записанный под `DELIMITER //`, пропадает

MySQL/MariaDB feature: триггер с телом `BEGIN … END`, записанный под
`DELIMITER`, чтобы клиент `mysql` отправил его одной инструкцией.

## Минимальный пример

```sql
DELIMITER //
CREATE TRIGGER t_bi BEFORE INSERT ON t FOR EACH ROW
BEGIN
  SET NEW.b = NEW.a;
END //
DELIMITER ;
```

## Вывод ora2pg (v25.0, `-m -t TRIGGER`)

```sql
\set ON_ERROR_STOP ON
```

И больше ничего: ни триггера, ни триггерной функции, ни ошибки, ни
строчки в логе.

## Наблюдаемая проблема

Разбор триггеров в ora2pg находит конец триггера по `;`. Под
разделителем, в котором `;` нет, он не находит триггер вовсе. Проверено:

| Разделитель | Сгенерировано триггеров |
|---|---|
| `;;` | 1 (сконвертирован) |
| `//` | 0 |
| `$$` | 0 |
| `\|` | 0 |
| `$` | 0 |

Схема загружается, а у таблицы в PostgreSQL триггера просто нет: всё, что
он делал — заполнение столбцов, аудит, поддержка сводной таблицы, — молча
перестаёт происходить. Ничего не падает, пока кто-нибудь не заметит
данные.

`;;` — выбор самого `mysqldump` для триггеров, так что дамп этим gap'ом не
затронут (его триггеры теряются по GAP-109); затронуты рукописные
скрипты, где подавляюще чаще встречаются `//` или `$$`.

**Воспроизводится: ДА.** Версия Ora2Pg: 25.0. Исходный диалект: MySQL
(`ora2pg -m`).

## Вердикт

**Gap подтверждён, severity high, failure_stage conversion** — потеря
видна только по тому, чего ora2pg не вывел, та же стадия, что у GAP-059.
Исправляется до конвертации: заменить разделитель на `;;` или убрать
директивы `DELIMITER`.

Реализовано: `ora2pg_gap_report/detectors/mysql_delimiter_trigger.py` —
отмечает каждый `CREATE TRIGGER`, перед которым действует разделитель без
`;`.
