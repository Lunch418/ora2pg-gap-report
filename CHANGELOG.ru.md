# Changelog

Формат по мотивам [Keep a Changelog](https://keepachangelog.com/ru/1.0.0/).
Проект следует [SemVer](https://semver.org/lang/ru/) в упрощённом виде,

## [Не выпущено]

### Добавлено

- **GAP-149..152: SQL Server и MySQL, проверенные на чужом коде** -
  Sakila от jOOQ (обе версии), база Employees, pubs, Northwind и Wide
  World Importers от Microsoft - с настоящими ora2pg 25.0 и PostgreSQL 16:
  - `mssql_statement_terminator`: команды, которые заканчиваются только
    `GO`, без `;` - ora2pg конвертирует первую и молча выбрасывает всё
    после неё (Sakila: вышла 1 таблица из 16). `--prepare` ставит `;` в
    конце каждой команды: 15 из 16, и последняя тоже, когда учтена
    команда, которая ничем не заканчивается перед следующим `CREATE TABLE`;
  - `mssql_index_name_collision`: одно имя индекса на нескольких
    таблицах, как в MySQL; `--prepare` переименовывает повторы;
  - `mssql_with_rollup`, `mysql_with_rollup`: `GROUP BY ... WITH ROLLUP`
    (и `WITH CUBE`); `--fix` пишет `GROUP BY ROLLUP (...)`.
- **GAP-143..148, найденные в том, чего не мог объяснить
  `--load-check`,** на чужом коде (utPLSQL, OraOpenSource Logger,
  библиотека Alexandria PL/SQL, демо-схемы Oracle). Каждый проверен на
  живом Oracle 23ai, ora2pg 25.0 и PostgreSQL 16:
  - `sequence_without_start`: `CREATE SEQUENCE s CACHE 100` получает
    пустой `START`, а голый `CREATE SEQUENCE s2` теряет последнюю цифру;
    `--prepare` дописывает `START WITH`, который подразумевает Oracle;
  - `param_default_spacing`: значение параметра `varchar2:= chr(10)`
    становится `VARCHAR2DEFAULT chr(10)`; `--prepare` расставляет пробелы;
  - `trim_leading_trailing`: `TRIM(LEADING x FROM y)` становится
    `trim(both leading ...)`; `--fix` убирает лишний BOTH;
  - `param_after_default`: параметр без значения по умолчанию после
    параметра со значением, PostgreSQL такое отвергает;
  - `hash_identifier`: имя с `#`;
  - `call_result_member`: `xml.extract(...).getstringval()`, `f(x).y` -
    ora2pg делает из этого `f[x].y`.

  На utPLSQL ошибок, которые не объясняет ни один пробел, стало 15
  вместо 28.

### Исправлено

- **Скрипт в UTF-16 читался как UTF-8 и выглядел чистым** - SSMS
  сохраняет скрипты в UTF-16, поэтому каждый второй байт был нулевым, и
  ничего не находилось (собственные примеры Microsoft). Теперь исходники
  читаются по метке порядка байтов (или, для UTF-16 без метки, по нулевым
  байтам) везде, где инструмент их читает; `--prepare` и `--fix`
  записывают такой файл обратно в его же кодировке.
- `--load-check` относит упавшую команду к `--fix`, только если
  исправление меняет строку с ошибкой или строку чуть выше: TRIM,
  исправленный в начале подпрограммы, больше не забирает синтаксическую
  ошибку ниже.
- **Подпрограмма после вложенной в теле пакета терялась молча** - ora2pg
  выбрасывает её вместе с подпрограммой, в которой есть вложенная
  (GAP-034; четыре подпрограммы OraOpenSource Logger). Теперь
  `nested_subprogram` сообщает и о ней, с пометкой "lost after".
- `--prepare` переписывал строку q'[...]' вне именованной подпрограммы, в
  анонимном блоке установочного скрипта, и ora2pg -t TABLE затем
  вытаскивал из удвоенных кавычек `''OFF''` (Logger). Такие строки теперь
  не трогаются.
- `param_after_default` указывает на строку подпрограммы, где PostgreSQL
  сообщает об ошибке, поэтому `--load-check` относит эту ошибку к GAP-146.

## [0.18.0] - 2026-10-10

### Добавлено

- **GAP-134..138: пять конструкций, вывод которых падает.** Каждая
  запущена в Oracle 23ai и, после ora2pg 25.0, в PostgreSQL 16:
  - `trunc_number`: `TRUNC` от числа становится `date_trunc` (ora2pg
    переписывает любой `TRUNC` как TRUNC даты) - вызов падает;
  - `float_precision`: `FLOAT(n)` в PL/SQL становится `double
    precision(n)` - подпрограмма не загружается; `--fix` убирает
    точность;
  - `plsql_integer_subtype`: `SIMPLE_INTEGER`, `NATURAL`, `POSITIVE`,
    `SIGNTYPE` копируются - подпрограмма не загружается; `--fix` пишет
    `integer` (`smallint`);
  - `instr_occurrence`: `INSTR` с позицией или вхождением копируется, а
    `instr` в PostgreSQL без orafce нет;
  - `date_arithmetic`: `d + 1`, `d1 - d2`, `TRUNC(d) - 7` с переменными
    DATE - `timestamp + integer` не существует, а разность - interval, а
    не число дней.

  Найдено и в OraOpenSource Logger и `file_util_pkg`: одиннадцать
  разностей дат и шесть вызовов `INSTR`.

- **GAP-139..142: `TO_CHAR`, `CHAR(n)` и `ROUND` от даты.** Каждый
  запущен в Oracle 23ai и, после ora2pg 25.0, в PostgreSQL 16:
  - `to_char_operator`: `TO_CHAR(a/b)` без пробелов становится
    `a/b::text`, где приведение относится только к `b`, - вызов падает
    (с пробелами ora2pg ставит скобки);
  - `to_char_default_format`: `TO_CHAR` даты или дроби без формата
    становится `x::text` - `2026-03-17 00:00:00` вместо `17-MAR-26`,
    `0.5` вместо `.5`;
  - `char_semantics`: `CHAR(n)` сохраняет тип, но PostgreSQL не
    учитывает хвостовые пробелы - `LENGTH` 2 вместо 5, `'ABx'` вместо
    `'AB   x'`, равенство с `VARCHAR2` там, где Oracle говорит "не
    равно" (один раз на файл);
  - `round_date`: `ROUND(d, 'MM')` и `ROUND(d)` копируются, а
    `round(timestamp)` в PostgreSQL нет.

  Проверено и не вошло: `ORDER BY ... DESC` ставит NULL первыми в обеих
  базах, а `TRUNC(d, 'MM'/'IW'/'Q')` переводится верно.

### Изменено

- **`--migrate` оставляет `NUMBER` десятичным.** ora2pg запускается с
  копией его собственного `ora2pg.conf`, записанной в
  `OUT_DIR/ora2pg.conf`, где `PG_NUMERIC_TYPE 0`, `DEFAULT_NUMERIC
  numeric` и `FLOAT:numeric`: `NUMBER` становится `numeric`,
  `NUMBER(10,2)` - `decimal(10,2)`, а не `bigint` и `double precision`
  (GAP-130, GAP-131, которые чек-лист тогда отмечает как учтённые). На
  образцах меняются только эти типы, результат загрузки тот же.
  `--keep-ora2pg-types` конвертирует с файлом как есть; если стандартный
  файл ora2pg прочитать нельзя, ничего не меняется.

### Исправлено

- **Проверено на чужом коде** - библиотека Alexandria PL/SQL, utPLSQL,
  OraOpenSource oos-utils и Logger, демо-схемы Oracle (около 240 000
  строк), с настоящими ora2pg 25.0 и PostgreSQL 16:
  - `--migrate` падал с внутренней ошибкой ("bad escape \w"), когда
    константа пакета хранила регулярное выражение: её значение читалось
    как шаблон замены;
  - склеенная ora2pg цепочка констант пакета со строковым литералом
    внутри (`'xmlns="'||g_ns||`) теперь тоже восстанавливается;
  - `trunc_number` следует правилу самого ora2pg: `TRUNC((n - 1) / 26)`
    ora2pg оставляет как есть, и оно работает - больше не помечается (так
    было с 20 из 72 находок);
  - `to_char_operator` находит и `TO_CHAR(abs(n - 1)+1)`, и
    `TO_CHAR((n+1))`, которые теряют скобки так же;
  - `empty_string_null` помечает `v := ''` и `DEFAULT ''` параметра,
    только если имя потом проверяется на NULL (53 -> 19: в основном это
    было `v := ''; v := v || x`, одинаковое в обеих базах);
  - `plsql_integer_subtype` и `float_precision` пропускают спецификации
    пакетов: их подпрограммы ora2pg конвертирует из тела.
- Тип переменной берётся из её собственного объявления, когда
  перегрузки одной подпрограммы объявляют один параметр по-разному
  (`tochar` в OraOpenSource Logger).

## [0.17.0] - 2026-10-10

### Добавлено

- **GAP-130..133: числа и `SUBSTR`, которые загружаются, а потом считают
  иначе.** Каждый запущен в Oracle 23ai и, после ora2pg 25.0, в
  PostgreSQL 16:
  - `number_without_precision`: `NUMBER` без точности становится `bigint`
    (ora2pg.conf из поставки: `DEFAULT_NUMERIC bigint`) - 9.99
    записывается как 10, `v := 2.5; RETURN v * 2` возвращает 6;
  - `number_as_float`: `NUMBER(p,s)` (p до 15) и `FLOAT` становятся
    `real`/`double precision` (`PG_NUMERIC_TYPE 1`) - `0.1 + 0.2 = 0.3`
    ложно, сумма десяти сумм по 0.1 - 0.9999999999999999;
  - `integer_division`: `7 / 2`, `i / 2` целых типов - в Oracle 3.5, в
    PostgreSQL 3 (найдено в OraOpenSource Logger: `1/1440`);
  - `substr_start`: `SUBSTR(s, 0, n)`, `SUBSTR(s, -n)` - другая часть
    строки (найдено в `file_util_pkg`: `substr(p_dir, -1)`).

  Первые два - это одна настройка каждый, поэтому сообщаются один раз на
  файл, а совет - проверенные строки ora2pg.conf: `DEFAULT_NUMERIC
  numeric`, `PG_NUMERIC_TYPE 0`, `DATA_TYPE FLOAT:numeric`.
- **"Не проверено": SQL, собранный во время выполнения.**
  `EXECUTE IMMEDIATE v_sql`, `OPEN c FOR v_sql`, `DBMS_SQL.PARSE`,
  `PREPARE ... FROM @v` в MySQL, `EXEC(@sql)` и `sp_executesql` в T-SQL
  выполняют SQL, который никакое сканирование не прочитает. Теперь каждый
  отчёт перечисляет их после находок - файл, строка, объект, команда,
  "частично", если строковые литералы в ней просканированы, - а в
  `MIGRATION.md` каждая становится пунктом, который отмечают после
  прогона на PostgreSQL. Это не находки, они ни на что не влияют;
  `--migrate` упоминает их в следующих шагах. JSON: массив `unchecked`,
  `schema_version` 3.

## [0.16.0] - 2026-10-10

### Добавлено

- **GAP-129 `empty_string_null`: `''`, который Oracle читает как NULL.**
  Первый пробел, где ничего не падает: `x = ''`, `v := ''`, `DEFAULT ''`,
  `NVL(x, '')` / `COALESCE(x, '')` ora2pg 25.0 копирует как есть (NVL -
  как `coalesce`), в PostgreSQL 16 всё загружается без ошибок, а потом
  возвращает другие результаты - в живом Oracle 23ai `gx_e2('')` даёт
  `other`, в PostgreSQL - `empty`. Остальные различия того же рода
  (склейка с NULL, `LENGTH('')`) зависят от данных; они описаны в
  исследовании, но не помечаются.
- **`--pg-version N`: целевая версия PostgreSQL.** Находки, которые на
  этой версии уже не проблема, не показываются, и stderr говорит, какие;
  `--load-check docker` и `--migrate` загружают в `postgres:N`. Учитывается
  только проверенное на той версии: пока это `JSON_TABLE` (GAP-017),
  вывод ora2pg с которым работает на PostgreSQL 17 и 18, - кроме записи
  Oracle с `ERROR ON ERROR` перед `COLUMNS`, у которой теперь свой текст.
  Для версии старше 16 выводится примечание, что пробелы подтверждены на
  16.
- **`--load-check` показывает корневые причины.** При первом прогоне
  упавшая таблица тянет за собой все представления, триггеры и
  подпрограммы на ней. Теперь каждая ошибка "нет нужного объекта" связана
  с упавшей командой, которая должна была создать объект (через эхо эха -
  до корня), корень говорит, сколько упало из-за него, а ошибки сведены по
  объектам: на примерах 41 такая ошибка сводится к 8 объектам, у каждого -
  "не создан, ошибка выше" или "нет в загруженных файлах". Это есть и в
  карточке загрузки HTML-отчёта, и в JSON (`caused_by`, `echoes`,
  `missing`).
  `schema_version` в JSON теперь 2.
- **Чеклист сохраняет галочку при переименовании.** Пункты были
  привязаны к объекту и файлу, и переименование файла или разделение
  пакета превращало отмеченный пункт в новый, открытый. Теперь галочка
  следует за объектом в переименованный или перенесённый файл и за
  подпрограммой в другой пакет, с пометкой "раньше было: ...", - только при
  однозначном соответствии.

### Изменено

- **Большой дамп сканируется за линейное время.** Имя объекта для
  находки искалось проходом по всем объектам перед ней, и большой файл
  обрабатывался за квадратичное время; у нескольких детекторов было то же
  самое. Монолитный дамп в 5 МБ шёл 41 с, теперь 22 с, а дамп в 10 МБ -
  45 с вместо нескольких минут, меньше чем в 200 МБ памяти. Шаблоны,
  которые не могут сработать - их слова нет в файле, - больше вообще не
  запускаются. Находки те же: сверено по каждой находке на всех примерах и
  фикстурах.

## [0.15.0] - 2026-10-09

### Добавлено

- **Docker-образ "всё в одном"**, `ghcr.io/lunch418/ora2pg-gap-report`: сам
  инструмент, ora2pg 25.0 (собран из того же закреплённого коммита, что и в CI)
  и psql, плюс docker CLI, чтобы `--load-check docker` работал через сокет хоста.
  С ним для `--migrate` не нужно ставить ничего, кроме docker. Публикуется на
  каждый релиз; CI собирает его на каждый PR и прогоняет внутри `--migrate` с
  проверкой загрузки.

- **`--migrate` исправляет по исходнику.** То, что вывод ora2pg теряет, а
  исходник ещё помнит, возвращается на место, и каждое исправление
  проверено на PostgreSQL 16 до и после: триггеры на команду остаются
  `FOR EACH STATEMENT` и возвращают `NULL` (GAP-118); константы пакетов со
  значением-литералом подставляются литералом везде, где ora2pg оставил
  чтение `current_setting()`, склеенный инициализатор GAP-114 или `DEFAULT`
  параметра с их именем (GAP-119); для MySQL-столбца `ENUM` добавляется его
  `CREATE TYPE` (GAP-068). На примерах пакетов: 43 исправления, ни одной
  ошибки загрузки GAP-114/119. Итог запуска считает их рядом с
  механическими.

- **Четыре новых gap'а, GAP-120..123**, из ошибок `--load-check` на
  примерах пакетов, которые не объяснял ни один gap; каждый подтверждён на
  живом Oracle 23ai, ora2pg 25.0 и PostgreSQL 16: `%TYPE` в RECORD или
  SUBTYPE пакета копируется в `CREATE TYPE`/`CREATE DOMAIN` (GAP-120); тип
  пакета в его собственных подпрограммах теряет имя пакета (GAP-121);
  процедура поставляемого пакета, вызванная как оператор (`DBMS_STATS`,
  `UTL_FILE`, `HTP`, ...), копируется без `CALL` (GAP-122);
  `DBMS_LOCK.SLEEP` становится `pg_sleep(n);` без `PERFORM` (GAP-123), это
  теперь чинит `--fix`. `--load-check` связывает их ошибки с ними,
  остатки `$IF` - с GAP-035, а метод коллекции пакета - с GAP-003: на
  примерах пакетов неизвестных ошибок осталось 2 вместо 9.

- **`--migrate` в TUI.** Кнопка «Миграция» рядом со «Проверить» открывает
  экран, где указываются каталог для результата, ora2pg и загрузка в
  PostgreSQL в docker; пока идёт работа, видны шаги, а в конце - та же
  сводка и тот же каталог, что и в командной строке. Кнопка
  «Сканировать» стала «Проверить», чтобы строка по-прежнему умещалась в
  80 колонок.

- **GitHub Action**: `uses: Lunch418/ora2pg-gap-report@<ref>` сканирует
  указанные пути, загружает SARIF в code scanning, по желанию пишет
  HTML-отчёт, отдаёт количества находок как выходы и последним проверяет
  порог `--fail-on`. Инструмент ставится из той же ссылки. CI запускает его
  в каждом pull request. См. `docs/ci-integration.ru.md`.

- **`MIGRATION.md` из `--migrate` говорит, что запуск уже сделал.** У
  пробела, который он подготовил в исходнике или исправил в `converted/`,
  есть пометка "`--migrate:` уже исправлено - проверьте и отметьте" (для
  констант пакетов - для тех, у которых значение-литерал), а не вид
  несделанной работы. Пункты остаются открытыми, чтобы их проверил
  пользователь.
  В `report.html` из `--migrate` такая же пометка есть в карточке пробела.

- **Ещё два gap'а, GAP-124 и GAP-125**, из прогона `--migrate` на выгрузке
  `GET_DDL` и скрипте SSMS, где каждое имя несёт схему (`"HR"."EMP"`,
  `[dbo].[Orders]`): ora2pg оставляет схему, но не создаёт её, и на чистом
  PostgreSQL ничего не загружается. На пути Oracle он к тому же убирает
  схему в триггерах и телах представлений, так что она нужна и в
  search_path; на пути T-SQL достаточно её создать, и теперь это делает
  `--fix` (`CREATE SCHEMA IF NOT EXISTS`). Подтверждено на живом Oracle
  23ai, ora2pg 25.0 и PostgreSQL 16.

- **GAP-126: подпрограмма T-SQL, за которой идёт `GO`**, как SSMS
  заканчивает каждый объект: ora2pg кладёт `GO` в тело (`END GO END;`), и
  подпрограмма не загружается. `--prepare --dialect mssql` теперь убирает
  строки `GO` и закрывает голый `END` точкой с запятой - в такой форме
  ora2pg конвертирует правильно; `--migrate` это применяет. Вместе с
  GAP-125 пример скрипта SSMS вместо 4 ошибок загрузки даёт ни одной.

- **Индексы из mysqldump подготовлены**: `--prepare --dialect mysql`
  теперь записывает `KEY idx (a)` как `INDEX idx (a)` (GAP-073: ora2pg
  превращал написание KEY в сломанный столбец), даёт имена безымянным
  индексам, которые ora2pg выбросил бы, и переименовывает имена индексов,
  общие для нескольких таблиц (**GAP-128**, новый: второй `CREATE INDEX`
  падал в PostgreSQL, где имя индекса принадлежит схеме). **GAP-127**,
  новый: индекс по префиксу столбца (`KEY idx (note(20))`) выходит с
  незакрытой кавычкой, которая проглатывает остаток файла; он помечается,
  а не переписывается - префиксных индексов в PostgreSQL нет.

## [0.14.0] - 2026-10-08

### Добавлено

- **`--migrate OUT_DIR`: весь путь одной командой.** Просканировать исходник
  (`report.html`, `MIGRATION.md`), подготовить копию (`--prepare`),
  сконвертировать её ora2pg по разу на тип объектов, применить `--fix` и с
  `--load-check` загрузить результат в настоящий PostgreSQL - всё в один
  каталог, исходник не трогается. ora2pg запускается на всех исходных файлах
  сразу, поэтому вызовы между пакетами конвертируются; `-t TYPE/FUNCTION/
  PROCEDURE` получают исходник без пакетов, потому что в файловом режиме они
  повторно вытаскивают члены пакетов без имени пакета. `--ora2pg-bin
  docker:IMAGE` запускает ora2pg из образа.
- README теперь начинается с пути миграции, а описание пакета на PyPI говорит,
  для чего инструмент.
- **GAP-114..119, найденные `--load-check` на настоящем коде.** Загрузка вывода
  ora2pg для open-source пакетов из `docs/research/samples/` показала ошибки,
  которые не объяснял ни один пробел реестра. Каждая сведена к минимальному
  примеру и подтверждена как обычно: живой Oracle 23ai, ora2pg 25.0 на записи,
  сделанной вручную, и на записи `DBMS_METADATA.GET_DDL`, PostgreSQL 16.
  - GAP-114 `package_constant_chain`: константа пакета из другой константы
    (`c_stamp := c_date || ' HH24'`) - ora2pg склеивает два вызова
    `current_setting()` в не-выражение, и каждая подпрограмма, читающая её, не
    загружается (две в OraOpenSource Logger).
  - GAP-115 `ref_cursor_type`: `TYPE x IS REF CURSOR` становится `CREATE OR
    REPLACE TYPE ... AS REFCURSOR`, такого синтаксиса в PostgreSQL нет.
  - GAP-116 `repeated_package_call`: `pkg.proc;` без скобок, когда та же
    подпрограмма его уже вызывала - повтор теряет `CALL`.
  - GAP-117 `trigger_package_call`: триггер вызывает процедуру пакета -
    триггеры конвертируются отдельно, и вызов копируется без `CALL`.
  - GAP-118 `statement_trigger`: триггер уровня команды выходит с `FOR EACH
    ROW` - загружается и срабатывает на каждую строку, а не раз на команду.
  - GAP-119 `package_constant_default`: константа пакета в умолчании
    параметра копируется как есть, хотя чтения в теле переписаны; функция не
    загружается (file_util_pkg из alexandria-plsql-utils, одиннадцать
    подпрограмм в Logger).
- **`--load-check` узнаёт, что оставляют в выводе пробелы, которые нельзя
  проверить по исходнику** (`CREATE TYPE ... AS REFCURSOR`, склеенные вызовы
  `current_setting()`, голые вызовы процедур), так что их ошибки загрузки
  привязываются к пробелу, хотя конструкции Oracle в выводе уже нет.
- **`--load-check TARGET`: загрузка сгенерированного кода в настоящий PostgreSQL.**
  Остальные режимы читают текст, а этот спрашивает сам PostgreSQL. Он передаёт вывод
  `ora2pg` в `psql` и раскладывает каждую команду, которая не загрузилась, по тому, что с
  ней делать: исправит `--fix`, известный пробел (с его GAP-NNN и `--explain`), ошибка,
  которой нет в реестре, эхо более ранней ошибки (нет таблицы или типа) или команда,
  которую проверка не может выполнить (`CREATE INDEX CONCURRENTLY`, отказ в правах). У
  каждой ошибки указаны файл и строка, на которые показал PostgreSQL.
  - `docker` запускает одноразовый контейнер `postgres:16-alpine` (порт не публикуется,
    после проверки контейнер удаляется), `docker:IMAGE` берёт другой образ, всё остальное
    считается строкой подключения libpq для локального `psql`.
  - Ничего не коммитится: все файлы выполняются в одной транзакции с `ON_ERROR_ROLLBACK`,
    которая в конце откатывается. Собственные `COMMIT`/`BEGIN` файлов и команды psql
    перед этим заменяются пробелами, так что номера строк не сдвигаются.
  - `ora2pg` пишет в каждый файл `SET check_function_bodies = false`, и тело PL/pgSQL,
    полное синтаксиса Oracle, загружается без разбора. Проверка включает разбор обратно,
    поэтому пробелы вида "падает при компиляции" действительно падают.
  - Файлы из каталога загружаются в порядке типов `ora2pg` (типы, последовательности,
    таблицы, представления, функции и процедуры, триггеры, индексы, ограничения, внешние
    ключи, права).
  - Код возврата `1`, если что-то не загрузилось, `2`, если проверку не удалось запустить.
    Вывод в терминал и в JSON, схема `schemas/load-check.schema.json`.

- **Рецепты миграции.** Пятнадцать страниц в `docs/recipes/`, по одной на
  класс проблем, а не на детектор: иерархические запросы, коллекции и массовые
  операции, автономные транзакции, состояние пакета, временные таблицы, PIVOT,
  многотабличный DML и upsert, обработка ошибок, database link, встроенные
  пакеты, аналитические функции, объекты только для чтения и невидимые объекты,
  секционирование, выражения T-SQL и MySQL, которые ora2pg копирует без
  изменений. В каждой - что делает ora2pg, приём для PostgreSQL и что не
  переносится, на английском и русском. Их SQL входит в тесты: каждая страница
  загружается в настоящий PostgreSQL 16 через `--load-check`, и её `ASSERT`
  должны выполниться, так что рецепт, который перестал работать, роняет
  сборку.
- **Каждый пробел ссылается на свой рецепт**: `--explain`, терминальный и
  HTML-отчёты, панель деталей TUI и `--load-check` показывают название и адрес
  рецепта, если он у пробела есть.
- **`--format checklist`**: работа по миграции как Markdown-список задач, по
  галочке на объект и пробел, у каждого пробела - что делать, рецепт и команда
  `--explain`. Повторная генерация в тот же `--output` сохраняет отметки, сама
  отмечает пункт, которого больше нет в файле, просканированном снова, и не
  трогает пункты из файлов, которые в этот раз не сканировались. Файл, который
  не является чеклистом этого инструмента, никогда не перезаписывается.
- **`--prepare`: исправить исходник до того, как его прочитает ora2pg.**
  Некоторые пробелы в выводе ora2pg уже не исправить: ora2pg потерял то, что
  для этого нужно. `--prepare` переписывает дамп в более простую форму, которую
  ждёт парсер ora2pg, не меняя того, что он определяет: блоки `DELIMITER` в
  MySQL (GAP-106, 107), `DEFINER=` (GAP-108), `/*!50003 ... */` вокруг
  определений (GAP-109) и `CREATE TABLE IF NOT EXISTS` (GAP-110); строки
  `q'[...]'` в Oracle (GAP-062) и `IF NOT EXISTS` (GAP-112); имена в
  `[скобках]` в T-SQL (GAP-087). Ведёт себя как `--fix`: по умолчанию diff,
  `--write` применяет, кодировка и концы строк файла сохраняются. Каждое
  переписывание подтверждено на ora2pg 25.0 и PostgreSQL 16, а тесты повторяют
  это с настоящим ora2pg (в задаче CI, где он есть) и с PostgreSQL с проверкой
  поведения. Отчёты, `--explain`, чеклист и блок "Дальше" называют команду
  там, где она нужна.
- **`--fix` исправляет GAP-024**: рекурсивный `WITH`, который ora2pg копирует без
  ключевого слова `RECURSIVE`, обязательного в PostgreSQL, его получает.
  Подтверждено как обычно: вывод ora2pg 25.0 для рекурсивного представления не
  загружается в PostgreSQL 16 (`relation "tree" does not exist`), исправленный
  загружается и обходит дерево. `WITH` с предложением `SEARCH`/`CYCLE` из Oracle
  оставлен человеку.
- **`--fix` исправляет GAP-075** - первое исправление для MySQL:
  `LIMIT смещение, количество`, которое ora2pg копирует как есть, а PostgreSQL
  отвергает (`LIMIT #,# syntax is not supported`), становится
  `LIMIT количество OFFSET смещение`. Только число или простое имя на каждом
  месте, как допускает MySQL, и никогда внутри строки, имени в кавычках или
  комментария. Подтверждено на выводе ora2pg 25.0 -m и PostgreSQL 16.
- **"Дальше" в конце терминального отчёта**: три команды, которые идут после
  сканирования, по порядку (чеклист, `--fix`, `--load-check`).

### Исправлено

  `exists $self->{partitions_list}{$table}{refrtable}` — проверку,
  задуманную только для обнаружения таблиц с partition-by-reference, но
  `exists` на многоуровневом разыменовании хеша — классическая ловушка
  Perl, которая молча авто-создаёт `partitions_list{$table}` для
  *каждой* обработанной таблицы, партиционирована она или нет.
  `_create_foreign_keys()` затем читает эту фантомную запись как
  доказательство, что целевая таблица партиционирована, и пропускает
  ограничение, но только когда `$self->{pg_version} <= 12` — а это ровно
  дефолт ora2pg (11) для конфига, в котором `PG_VERSION` никогда не
  задавали. Проверено на четырёх комбинациях (файловый вход и живое
  подключение к MariaDB, скрещённые с `PG_VERSION` не заданным/12 против
  13), и то же самое подтверждено для MSSQL: триггер — `PG_VERSION`, а не
  режим входа и не диалект. Оба research-документа (английский и
  русский) и оба докстринга детекторов переписаны заново, чтобы это
  отразить; сама находка (`FOREIGN KEY` молча пропадает при настройках
  по умолчанию) была верна всё это время, ошибочным раз за разом
  оказывалось только объяснение «почему».

  `MSSQL.pm`, плюс `_get_identities()` и запрос стартового значения
  `AUTO_INCREMENT` через `INFORMATION_SCHEMA.TABLES`) всегда обращаются к
  исходной базе живьём, без какого-либо разбора DDL-текста как запасного
  пути, поэтому файловый режим, который сканирует этот проект, теряет все
  четыре независимо от списка типов экспорта. Исправлены четыре
  research-документа, докстринги соответствующих детекторов,
  `GAP_REGISTRY.md` и `README.md` — теперь там верный механизм и явная
  оговорка про файловый путь; в GAP-082 и GAP-080 добавлено сравнение с
  живым режимом, подтверждённое на реальном экземпляре MariaDB. Сами
  находки не изменились: именно это файловый путь (и его air-gapped
  пользователи) реально получают, проверено до и после правки.
- Замена на `citext` в GAP-103 (`mssql_collation`) — это документированная
  опция ora2pg, `CASE_INSENSITIVE_SEARCH`, по умолчанию равная `citext`
  для источников MSSQL, а не необъяснённый хардкод; документ и докстринг
  детектора это теперь отражают. Находка не изменилась: опция проверяет
  только базовый тип столбца, а не его реальный `COLLATE`, поэтому
  значение по умолчанию по-прежнему молча превращает регистрозависимый
  столбец в регистронезависимый.

### Исправлено
- **Закрытый канал больше не выдаётся за баг инструмента.** `... | head`
  или выход из `... | less` закрывают читающий конец, пока скан ещё
  пишет; возникавший `BrokenPipeError` доходил до верхнеуровневого
  обработчика в `main()`, который предлагал завести issue на GitHub и
  завершался с кодом 3 — из-за обычного пайплайна в шелле. Теперь всё
  заканчивается тихо: SIGPIPE возвращается к поведению по умолчанию
  (Python при старте ставит ему `SIG_IGN`, из-за чего сигнал и
  превращается в исключение), поэтому `... | head` завершается так же,
  как `cat ... | head` — процесс убивается сигналом, молча, а shell
  сообщает 141. Перехват исключения не удавалось сделать столь же тихим:
  интерпретатор всё равно сбрасывает `sys.stdout` при завершении, и на
  macOS это печатало «Exception ignored in: <_io.TextIOWrapper ...>» даже
  с файловым дескриптором, перенаправленным в `os.devnull`. На Windows
  SIGPIPE нет и, как выяснилось, `BrokenPipeError` там для этого случая не
  возбуждается вовсе: запись в канал, у которого не стало читателя,
  возвращается обычным `OSError` с `EINVAL` — он проваливался в общий
  обработчик и давал ровно то самое «сообщите о баге», ради которого всё
  это и правится. Проверка закрытого канала теперь распознаёт и такой
  случай (`EINVAL` — только на Windows, потому что в остальных системах
  это настоящий неверный аргумент) и возвращает 141, предварительно сливая
  stdout в `os.devnull`: без этого падающий финальный сброс буферов
  завершал процесс с кодом 120 независимо от того, что вернул `main()`. 141
  намеренно вне диапазона 0/1/2/3 — каждый из них описывает скан,
  дошедший до конца.
- Внутренние ошибки теперь сообщаются на языке, который запросили через
  `--lang`. Верхнеуровневый обработчик определял язык заново и игнорировал
  флаг, поэтому при `--lang en` сообщение о падении выходило по-русски.
- **`--help` больше не падает на консоли Windows.** Русский — молчаливый
  язык по умолчанию, а на западной Windows-консоли кириллицы нет вовсе:
  argparse писал русскую справку прямо в `sys.stdout`,
  `UnicodeEncodeError` доходил до верхнеуровневого обработчика в
  `main()`, и первая же команда нового пользователя сообщала
  «непредвиденная внутренняя ошибка» и завершалась с кодом 3 при пустом
  stdout. Теперь выбор по умолчанию проверяет, может ли поток закодировать
  русский, и отдаёт английский, если не может; явные `--lang ru`,
  переменная окружения и сохранённый выбор по-прежнему уважаются. Найдено
  новым тестом `python -m` — первым в наборе, который запускает CLI
  настоящим подпроцессом: вызов `main()` внутри процесса это не
  воспроизводит, потому что кодировщик существует только у реального
  потока.
- **Ряды контролов на экране сканирования в TUI больше не разъезжаются,
  не обрезаются и не схлопываются.** Три дефекта с одной причиной —
  ширины выводили рассуждением, а не измерением:
  - Три пикера были рассчитаны по самой длинной подписи, без учёта рамки
    и стрелки выпадающего списка, которые Select рисует вокруг неё.
    Недомеренный Select не вылезает вбок — он переносит свой текст и
    становится на строку выше соседей, оставляя рваный нижний край.
    Теперь ширины — измеренный минимум, при котором каждый рендерится
    высотой 3 (dialect 12 -> 14, language 13 -> 15, severity 20 -> 22;
    последний был высоким только в английском).
  - Ряд с CONNECT BY требовал 87 колонок в русском и 84 в английском при
    пределе 80, поэтому подпись чекбокса обрезалась посреди слова.
    Textual обрезает молча — ничего не падает, и сам виджет выглядит
    правильным.
  - Поле пути baseline занимает `1fr` рядом с чекбоксом авто-ширины, и
    «сколько осталось» составляло 10 колонок в русском: поле для пути к
    файлу, показывающее десять символов пути. Теперь 30.
  - Всё закреплено проверками геометрии, параметризованными по каждому
    ряду экрана и обеим локалям, плюс отдельной, отличающей «ряд влезает»
    от «полем можно пользоваться». На старых значениях они падают.

  конструкциях, и часть поломок полностью молчаливая — отсюда первые в
  реестре записи с `failure_stage="semantic"`.

  Падают на загрузке схемы (`deployment`):
  - `mysql_key_index` (GAP-073) — `KEY <имя> (<столбцы>)`, то самое
    написание, которое mysqldump выдаёт по умолчанию для каждого
    вторичного индекса, остаётся обрубком `key <ИМЯ>` на месте
    определения столбца. Самый широкий по охвату gap партии. Синоним
    `INDEX` и `UNIQUE KEY` переносятся корректно и намеренно не
    помечаются.
  - `mysql_spatial_index` (GAP-074) — `SPATIAL KEY`/`SPATIAL INDEX`, та же
    форма поломки, но другая починка (GiST-индекс поверх PostGIS-типа).

  - `mysql_limit_comma` (GAP-075) — `LIMIT <смещение>, <количество>`;
    PostgreSQL такую форму не принимает. Порядок аргументов обратный.
  - `mysql_replace_into` (GAP-076) — `REPLACE INTO`, копируется дословно.
  - `mysql_insert_ignore` (GAP-077) — `INSERT IGNORE`, копируется дословно.
  - `mysql_prepare_from` (GAP-078) — `PREPARE <имя> FROM <строка>`; у
    PostgreSQL свой PREPARE, с `AS <запрос>`, а не строковой переменной.
  - `mysql_last_insert_id` (GAP-079) — `LAST_INSERT_ID()`, такой функции
    в PostgreSQL нет.
  - `mysql_auto_increment_start` (GAP-080) — опция таблицы
    `AUTO_INCREMENT=<n>` теряется, последовательность стартует с 1, и
    первая же вставка после переноса данных падает на первичном ключе.

  - `mysql_date_format` (GAP-081) — `DATE_FORMAT(...)` превращается в
    голый конструктор кортежа: имени `to_char` нет, `%d` не переведён;
    запрос молча возвращает пару вместо отформатированной строки.
  - `mysql_foreign_key` (GAP-082) — внешние ключи выбрасываются целиком, и
    отдельного типа экспорта под них у ora2pg нет; ссылочная целостность и
    каскады просто перестают существовать.
  - `mysql_zero_date` (GAP-083) — `'0000-00-00'`, признак «не задано»,
    молча превращается в настоящую дату `'1970-01-01'`.
  - `mysql_declare_handler` (GAP-084) — `DECLARE ... HANDLER`
    выбрасывается, `EXCEPTION`-блок взамен не появляется, и то, что MySQL
    глушил, теперь обрывает транзакцию вызывающего.
  - `mysql_collate` (GAP-085) — `COLLATE`/`CHARACTER SET` на столбце
    выбрасывается; регистронезависимые правила MySQL становятся
    регистрозависимым сравнением PostgreSQL, и запросы молча возвращают
    другие строки.
  - `mysql_set_type` (GAP-086, `medium`) — `SET(...)` становится обычным
    `text`; схема работает и данные сохраняются, но проверки будущих
    записей больше нет.
- T-SQL / SQL Server как третий source-диалект (`--dialect mssql`,
  source-side для `ora2pg -M`) и **19 подтверждённых gap'ов,
  GAP-087..105** — реестр вырос с 86 до 105. Механика та же, что у
  MySQL-диалекта: новый лексер `mssql_lex.py` (идентификаторы в
  квадратных скобках, вложенные блочные комментарии, экранирование строк
  только удвоенной кавычкой, имена `@переменная`/`#temp`), собственный
  кортеж `_MSSQL_DETECTORS` в `core.py` и `mssql` в списке значений
  `--dialect`. Каждый gap подтверждён так же, как в двух других
  диалектах: минимальный пример, реальный прогон `ora2pg 25.0 -M`,
  загрузка сгенерированного вывода на живой PostgreSQL 16 — а для
  молчаливых ещё и реально выполненный на живых данных запрос.

  Всю партию определяют две находки. `mssql_bracket_identifier`
  (GAP-087) в одиночку кладёт практически любой реальный скрипт: на
  файловом пути ora2pg не снимает квадратные скобки T-SQL, и
  `CREATE TABLE [dbo].[Orders] ( [Id] [int] ... )` превращается в
  `CREATE TABLE "[dbo]"."[orders]" ( "[id]" [INT] ... )`, который не
  загружается, — а SSMS по умолчанию берёт в скобки каждое имя. Та же
  таблица без скобок конвертируется корректно; в исходниках ora2pg видно
  почему: снятие скобок есть только внутри подпрограмм, работающих с
  живым подключением. Второе — `mssql_update_set` (GAP-089), который
  портит *каждый* UPDATE в каждой процедуре, принимая его SET за
  одноимённый оператор присваивания T-SQL и выдавая
  `UPDATE t col := val`.

  Падают на загрузке схемы (`deployment`): `mssql_bracket_identifier`
  (087), `mssql_newid_default` (088 — `uuid_generate_v4()` без
  `CREATE EXTENSION "uuid-ossp"`).

  Падают на первом реальном вызове (`runtime`): `mssql_update_set` (089),
  `mssql_identity_column` (090 — IDENTITY пропадает целиком, проверено:
  обычная вставка потом падает на NOT NULL),
  `mssql_parameterless_procedure` (091 — неразбираемый пустой
  `DECLARE ;`, изолировано сравнением с той же процедурой с параметром),
  `mssql_if_statement` (092 — нет `END IF` с блоком, нет `THEN` без
  него), `mssql_raiserror` (093), `mssql_try_catch` (094),
  `mssql_top_clause` (095), `mssql_scope_identity` (096),
  `mssql_output_clause` (097), `mssql_iif` (098), `mssql_datediff` (099 —
  при том что соседние DATEADD/DATEPART переводятся верно) и
  `mssql_charindex` (100 — переведён в `position()`, но с удвоенными
  кавычками, то есть в невалидный SQL).

  Не дают ошибки вообще (`semantic`): `mssql_filtered_index` (101 —
  выбрасывается, хотя в PostgreSQL есть ровно такой же синтаксис),
  `mssql_foreign_key` (102 — выбрасывается так же, как на MySQL-стороне),
  `mssql_collation` (103 — все строковые столбцы становятся
  регистронезависимым citext; проверено на живых данных, что столбец с
  `_CS_`-правилом начинает находить значение в другом регистре),
  `mssql_computed_column` (104 — тип citext независимо от того, что
  считает выражение) и `mssql_rowversion` (105 — становится bytea,
  который никогда не обновляется сам, и оптимистичная блокировка молча
  перестаёт ловить конфликты).

- **`--verify` показывает то, что внесла сама конверсия.** Раньше он
  перебирал только детекторы из baseline, поэтому конструкция, которой не
  было в исходнике Oracle, но которая появилась в выводе ora2pg, молча
  выбрасывалась — ровно то, о чём проверка «не сломала ли конверсия
  вывод» обязана сообщать в первую очередь. Теперь это отдельная секция
  (ключ `new_in_output` в `--format json`, панель в терминальном отчёте,
  свои строки в TUI), отдельно от основной таблицы: сравнивать «до/после»
  тут не с чем.

- **Код возврата `3` для внутренних ошибок.** Непойманное исключение
  раньше давало `1` — тот же код, которым `--fail-on` сообщает «гейт не
  пройден», так что в CI упавший анализатор было не отличить от гейта,
  который честно отработал и нашёл проблемы. Теперь четыре кода
  различаются и описаны в README: `0` чисто, `1` гейт не пройден, `2`
  ошибка использования или непросканированный вход, `3` внутренняя
  ошибка.

### Fixed
- **Diff от `--fix` нельзя было скормить `git apply`/`patch`.**
  `Console.print()` из Rich переносит текст по ширине терминала — а когда
  stdout не терминал, по фиксированным 80 колонкам, то есть ровно в
  сценарии `--fix > out.patch`, ради которого режим и существует.
  Перенесённая строка заголовка `---`/`+++` или строка ханка — это битый
  diff, `git apply` отвергает его целиком; достаточно было пути подлиннее.
  Теперь diff идёт мимо разметки Rich, а все статусные строки уехали в
  stderr, так что в режиме `--fix` на stdout только байты diff'а — сколько
  бы файлов ни оказалось чистыми.

- **Baseline мог разойтись сам с собой из-за формы записи пути.**
  `group_key()` хешировал `source_file` ровно в том виде, в каком путь
  пришёл в `argv`, поэтому `tool pkg.sql --save b.json`, а затем
  `tool "$PWD/pkg.sql" --baseline b.json` показывал одну и ту же
  нетронутую находку и как NEW, и как RESOLVED. Теперь путь перед
  хешированием резолвится и берётся относительно рабочей директории —
  заодно поглощаются `./`, хвостовой слеш и сегменты `..`.
  **`schema_version` поднят до 2**: снапшот от старой версии честно не
  загрузится с понятным сообщением, вместо того чтобы молча дать неверные
  NEW/RESOLVED по новой формуле. Перезапишите его через `--save`.

- **Сканирование было квадратичным по размеру файла.** `line_at()` считал
  переводы строк от начала файла на каждом вызове, а вызов — на каждую
  находку: O(n²) на скан. Теперь предвычисленные смещения строк и
  `bisect`, с кэшем ровно как у масок: 5 720 обращений на файле 1,6 МБ —
  вместо ~5,6 с стало 0,067 с. Одна и та же строка была во всех трёх
  лексерах.

- **Два T-SQL-детектора срабатывали на обычном корректном SQL.**
  `\bIF\s+` ловил каждый `DROP TABLE IF EXISTS` в идемпотентном
  SSMS-скрипте, а `IDENTITY` без правой границы слова — столбец с именем
  `IDENTITY_FLAG`. Оба детектора выдают `high`, так что обе ложные
  находки оказывались наверху отчёта. `IF EXISTS`/`IF NOT EXISTS` теперь
  исключены — с честно записанным компромиссом: настоящий условный
  `IF EXISTS(...) BEGIN ... END` тоже перестаёт отмечаться, потому что
  регуляркой эти два случая не различить, а молчание тут — меньшее зло,
  чем шум на каждом идемпотентном скрипте.

- **Один упавший детектор больше не стоит всего прогона.** У
  `scan_source()` появилась опциональная изоляция по детекторам: упавший
  теряет только свои находки по этому файлу — результаты всех остальных
  детекторов по нему и все остальные файлы возвращаются как обычно, а имя
  упавшего детектора печатается в stderr. Уровнем выше так же изолированы
  сами файлы. В TUI то же самое: исключение в рабочем потоке раньше
  роняло всё приложение Textual вместо показа предупреждения.

- **Запись файлов атомарна и создаёт родительскую директорию.** Снапшот
  baseline, отчёт и — что важнее всего — собственный SQL пользователя под
  `--fix --write` писались прямо в целевой путь, поэтому падение или
  нехватка места посреди записи оставляли усечённый файл на месте
  целого. Теперь запись идёт во временный файл в той же директории и
  переименованием встаёт на место. `--save reports/base.json` в
  несуществующую директорию работает, а не падает с голым `[Errno 2]`.

- `dialect_of_detector()` пересобирал полный кортеж имён детекторов
  каждого диалекта на каждом вызове, а `--verify` зовёт его на каждую
  запись baseline: снапшот на тысячу находок — тысяча пересборок одной и
  той же таблицы.

### Changed
- CI гоняется ещё и на `windows-latest` и `macos-latest`, и все три
  платформы блокирующие. Платформозависимая поверхность (работа с
  путями, атомарные переименования, декодирование вывода subprocess,
  регистронезависимое сопоставление расширений, существующее ради
  Windows-тулинга) до сих пор ни разу реально не исполнялась ни на одной
  из этих ОС.

  И с первого же прогона нашла настоящий баг: `ora2pg_wrapper.py`
  запускал `ora2pg` через `subprocess.run(..., text=True)` без явной
  кодировки, поэтому на Windows его вывод декодировался как cp1252 — и
  любой не-ASCII байт в выводе самого ora2pg (а проект подставляет его
  `stderr` в свои сообщения об ошибках) превращался в
  `UnicodeDecodeError` из недр `subprocess`. Исправлено — вместе с ~80
  чтениями и записями файлов в тестах и скриптах с той же скрытой
  проблемой. `EncodingWarning` теперь ошибка в тест-сьюте, а CI включает
  её через `PYTHONWARNDEFAULTENCODING`, так что заново завести чтение с
  локальной кодировкой вместо UTF-8 уже не получится.
- У `rich` и `textual` появились верхние границы версий с записанным
  обоснованием — так же, как это уже было у `ruff`: инструмент обещает
  воспроизводимый вывод и поставляется офлайн-бандлом, так что тихий
  мажорный апгрейд на очередном `pip install` — реальный риск. Нижняя
  граница `setuptools` на время сборки поднята выше уязвимой ветки 68.x.

### Известное и отложенное
Найдено тем же аудитом и намеренно не сделано здесь — каждый пункт
крупный рефакторинг, риск которого не стоит брать в один релиз с
исправлениями выше и без ревью:
- 83 детектора — это один 15-строчный шаблон, повторённый; они могли бы
  быть декларативной таблицей и фабрикой.
- Три лексера по большей части совпадают и могли бы стать общими
  примитивами за протоколом диалекта.
- Пять реестров метаданных gap'ов могли бы быть одним `GapEntry`.
- Сопоставление блоков в лексере рекурсивное, а не на явном стеке.
  Исправление кодов возврата и изоляции выше закрывает симптом падения в
  любом случае, но сама рекурсия по-прежнему не ограничена.

Отдельно, и не из аудита: `scan_source()` целиком по-прежнему растёт
чуть хуже линейного на очень больших входах (файл в 50× занял ~69×
времени после починки `line_at()` — против ~230× до неё). Квадратичное
слагаемое, на которое указывал аудит, устранено; остальное — в другом
месте и ещё не профилировалось.

  - `ignore_nulls` (GAP-048) — `IGNORE NULLS`/`RESPECT NULLS` у
    аналитических функций, копируется как есть; в PostgreSQL 16 такого
    синтаксиса нет вообще.
  - `nlssort` (GAP-049) — переписывается в `COLLATE "GERMAN"`, а
    сортировки с таким именем в PostgreSQL нет.
  - `anydata_type` (GAP-051) — `SYS.ANYDATA`/`ANYDATASET`/`ANYTYPE`
    переносится как имя типа; ни такого типа, ни схемы `SYS` нет.
  - `system_trigger` (GAP-052) — триггер `ON DATABASE`/`ON SCHEMA`
    выводится как обычный табличный, на таблицу с именем
    `database`/`schema`, с сохранением Oracle-события.
  - `table_collection` (GAP-054) — оператор разворота коллекции
    `TABLE(...)`, копируется как есть.
  - `cursor_expression` (GAP-055) — `CURSOR(SELECT ...)`, как есть.
  - `for_update_wait` (GAP-056) — `FOR UPDATE ... WAIT n`; у PostgreSQL
    там есть только `NOWAIT` и `SKIP LOCKED`.
  - `rownum_dml` (GAP-057) — `ROWNUM` в `UPDATE`/`DELETE` переписывается в
    `LIMIT`, который PostgreSQL в DML не принимает. Во вложенном
    подзапросе намеренно **не** помечается: эта форма конвертируется
    корректно, проверено выполнением.
  - `subtype_range` (GAP-061) — `SUBTYPE ... RANGE lo .. hi` переносится в
    `CREATE DOMAIN` дословно.
  - `sdo_geometry` (GAP-067, единственный `medium` в партии) —
    отображается в тип PostGIS `geometry` без нужной ему строки
    `CREATE EXTENSION postgis`.

  Загружаются чисто и падают при первом выполнении (`runtime`):
  - `long_raw_type` (GAP-050) — `LONG RAW` отображается в `text`, из-за
    чего двоичные данные вообще не загрузить.
  - `trigger_follows` (GAP-053) — `FOLLOWS`/`PRECEDES` попадает **внутрь**
    тела сгенерированной функции и ломает любую запись в таблицу.
  - `pragma_exception_init` (GAP-060) — все обработчики схлопываются в
    `SQLSTATE '50001'`, который PostgreSQL не возбуждает никогда.
  - `alt_quote_literal` (GAP-062) — альтернативные кавычки `q'[...]'`.
  - `goto_statement` (GAP-063) — `GOTO`; в PL/pgSQL его нет.
  - `cursor_rowtype` (GAP-064) — `<курсор>%ROWTYPE`; PL/pgSQL допускает
    `%ROWTYPE` только от таблицы или представления.
  - `wm_concat` (GAP-065) — копируется как есть, в отличие от `LISTAGG`.

  Не вызывают ошибки вообще никогда (`semantic`):
  - `to_date_rr` (GAP-058) — формат `RR` внутри `TO_DATE` остаётся на
    месте, и PostgreSQL молча возвращает 1 год до нашей эры.
  - `read_only_view` (GAP-066) — `WITH READ ONLY` выбрасывается;
    полученное представление автоматически обновляемое, поэтому запись,
    которую Oracle запрещал, теперь молча проходит.

  Вообще не доходят до вывода (`conversion`):
  - `authid_clause` (GAP-059) — процедуру с `AUTHID CURRENT_USER` или
    `AUTHID DEFINER` ora2pg выбрасывает целиком: ни вывода, ни ошибки, ни
    даже строки DEBUG в логе. Подтверждено контрольным прогоном той же
    процедуры без оговорки — она конвертируется штатно.

- `plsql_lex.mask_comments_only()` — третий режим маскировки рядом с
  `mask_strings_and_comments()` и `mask_dynamic_sql_visible()`, из того же
  токенизатора и с тем же контрактом сохранения длины и переносов.
  GAP-058 и GAP-062 оба **про сам строковый литерал** (формат `RR`,
  литерал `q'...'`), который два существующих режима затирают, а
  сканирование сырого исходника ловило бы ещё и закомментированный код.

### Performance

  `enclosing_object_name_index()` (`plsql_lex.py`) теперь кэшируются
  (`functools.lru_cache`) — ~37 детекторов каждый вызывали
  `mask_strings_and_comments()` с одним и тем же `source` при
  сканировании одного файла (треть из них — ещё и
  `mask_dynamic_sql_visible()`/`enclosing_object_name_index()`), заново
  пересчитывая один и тот же O(n) проход по файлу по 20-70 раз. На
  `docs/research/samples/logger.pkb` (80 КБ) — `scan_source()` с

  заодно возвращает `tuple`, а не `list` — при разделяемом кэшированном

### Security
- `--format csv`: поле, начинающееся с `=`, `+`, `-`, `@`, табуляции или
  CR (снятое напрямую со сканируемого Oracle-кода — `snippet`/
  `object_name`/`source_file`), теперь экранируется ведущим `'` —
  предотвращает выполнение формулы при открытии отчёта в Excel/Sheets/
  LibreOffice (formula injection).
- `--format sarif`: `artifactLocation.uri` больше не берёт сырой
  файловый путь как есть — теперь это валидный URI-reference (RFC 3986,
  через `urllib.parse.quote`), с учётом Windows-путей (`\`, `:` буквы
  диска). Раньше документ мог быть невалидным SARIF (просто ни разу не
  пойманным существующими тестами: `jsonschema.validate()` без явного
  `FormatChecker` не проверяет ограничение `format: uri-reference`).

### Fixed
- `--tui`: любое сканируемое содержимое (имя файла, объекта, сниппет,
  сообщение), попадавшее в `Static.update()`/`DataTable.add_row()` как
  обычная строка, парсилось Textual как собственная markup-разметка —
  квадратная скобка в реальном коде или пути (`arr[i][j]`, `notes[archive]`)
  могла упасть с ошибкой разметки или исказить вывод. Весь такой текст
  теперь оборачивается в `rich.text.Text(...)`, тот же приём, что уже
  применялся в `terminal_report.py`.
- `--save`/`--baseline`, указывающие на один и тот же файл, раньше молча
  перезаписывали снапшот и сравнивали прогон сам с собой — теперь явная
  ошибка (сравнение по разрешённому пути, ловит и разное написание одного
  файла).
- `--save` больше не пишет baseline-снапшот, если сканирование было
  частичным (были ошибки чтения файлов) — такой снапшот не является
  надёжной точкой отсчёта для последующего `--baseline`.
- `--explain` проверял конфликт только с частью флагов сканирования
  (`--fail-on`, `--save`, `--baseline`, `--check-connect-by`) — теперь
  учитывает и `--verify`, `--format`, `--output`, `--severity`, `--object`,
  и текст ошибки перечисляет их все.
- `load_baseline()` требовал полный набор полей JSON Schema у каждой
  записи находки — старые снапшоты `--save`, сохранённые до появления
  `gap_number`/`failure_stage`, отклонялись. Теперь обязательны только
  реально используемые без `.get()` поля (`group_key`, `detector`).
- Несколько мест читали файл через `read_text(errors="replace")` без
  явной кодировки — на платформе с отличной от UTF-8 локалью это могло
  привести к чтению в неверной кодировке вместо честного `UTF-8` +
  replacement-символов на невалидных байтах.
- `package_state`: детектор смотрел только на объявления в `PACKAGE BODY`
  и пропускал `CONSTANT` — оба случая на практике получают тот же
  сломанный `set_config`/`current_setting`-рерайт ora2pg, что и обычная
  переменная (проверено реальным прогоном ora2pg 25.0, см.
  `docs/research/gap-036-package-state.md`). На реальном
  `logger.pkb` из тестового корпуса это было 22 непосчитанные находки.
- `recursive_with`: `WITH seed AS (...), tree AS (...)` — рекурсивный CTE,
  не первый в списке `WITH`, — не детектировался вообще, так как
  регулярное выражение требовало ключевое слово `WITH` непосредственно
  перед именем CTE.
- `bulk_collect`: проверка «это локальное объявление TYPE, а не
  `CREATE TYPE` уровня схемы» пересканировала весь префикс файла заново
  на каждое совпадение — O(n²) на файле с большим числом локальных
  `TYPE`-объявлений. Заменено на один проход вперёд с построением набора
  позиций.

## [0.4.0] - 2026-08-16

### Added
- 7 новых детекторов, GAP-022…GAP-028. Реестр — теперь 28 подтверждённых
  gap'ов, см. `docs/research/GAP_REGISTRY.md`:
  - `cross_apply` — `CROSS APPLY`/`OUTER APPLY`, синтаксиса `APPLY` нет в
    PostgreSQL вообще.
  - `oracle_text` — домен-индекс `INDEXTYPE IS CTXSYS.*` (Oracle Text)
    отбрасывается целиком; вызовы `CONTAINS`/`CATSEARCH`/`MATCHES` не
    переносятся.
  - `recursive_with` — нативная рекурсивная `WITH ... AS (...)` (не через
    `CONNECT BY`) без обязательного в PostgreSQL ключевого слова
    `RECURSIVE`.
  - `invisible_index` — индекс `INVISIBLE` теряет своё скрытие от
    оптимизатора.
  - `read_only_table` — `CREATE TABLE ... READ ONLY` теряет гарантию
    неизменяемости; `INSERT` проходит там, где Oracle гарантированно
    блокирует его (`ORA-12081`).
  - `materialized_view_log` — `CREATE MATERIALIZED VIEW LOG` не
    конвертируется вообще, след только в DEBUG-логе.
  - `identity_column` — `GENERATED ... AS IDENTITY (...)` с опциями:
    настоящий баг двойных скобок в самой подстановке ora2pg (не пропуск
    конвертации, а поломанная конвертация — код падает при загрузке DDL).
- `docs/research/AUDIT.md` и `scripts/audit_gap_test_counts.py` обновлены
  под все 28 gap'ов.

### Fixed
- Системный баг статeмент-скоупинга: `DBMS_METADATA.GET_DDL` (этот же
  проект использует его для выгрузки DDL из Oracle) по умолчанию не
  ставит `;` в конце оператора, а часть детекторов ограничивала «свой»
  оператор как «до следующей `;`, а если её нет — до конца файла», из-за
  чего конструкция из более поздней таблицы могла ошибочно приписаться
  более ранней, незавершённой. Затронуло в том числе уже опубликованные
  `table_partitioning` и `external_table`, не только новые детекторы этого
  релиза. Добавлен общий хелпер `statement_end()` в `plsql_lex.py`,
  применён в 8 детекторах: `table_partitioning`, `external_table`,
  `invisible_column`, `global_temp_table`, `oracle_text`,
  `invisible_index`, `read_only_table`, `identity_column`.
- `invisible_index`/`read_only_table`: ложные срабатывания на столбце с
  тем же именем, что и модификатор (`invisible`/`read_only` как
  идентификатор столбца, в том числе в двойных кавычках) — теперь
  исключены.
- `invisible_index`/`read_only_table`/`oracle_text`: номер строки в
  находке теперь указывает на сам модификатор/секцию (`INVISIBLE`/`READ
  ONLY`/`INDEXTYPE IS ...`), а не на строку с открывающим `CREATE
  TABLE`/`CREATE INDEX` — важно для многострочного DDL.
- `materialized_view_log`: severity поднята с `medium` на `high` — тот же
  профиль риска, что у `table_partitioning`/`external_table` (конструкция
  молча пропадает без ошибки PostgreSQL, но означает реальную
  архитектурную потерю).

  implicit-default — см. `[tool.ruff.lint]` в `pyproject.toml`).

### Fixed
- Атрибуция находок (`object_name` в отчёте) для реального кода, а не
  только синтетических примеров — найдено прогоном инструмента на двух
  больших открытых PL/SQL-кодовых базах (`mortenbra/alexandria-plsql-utils`,
  `oracle-samples/db-sample-schemas`, суммарно ~143k строк):
  - `PACKAGE`-спецификация (без `BODY`) и `CREATE VIEW`/`CREATE MATERIALIZED
    VIEW` теперь распознаются как контейнеры для атрибуции — раньше
    находки внутри них уходили в `UNKNOWN`.
  - `CREATE`-конструкция внутри списка привилегий `GRANT`/`REVOKE`
    (`GRANT ..., CREATE VIEW TO oe;`) больше не принимается за настоящее
    объявление объекта.
  - Строчные комментарии SQL*Plus (`REM`/`REMARK`) теперь маскируются —
    раньше реальное объявление, которому предшествовали только такие
    комментарии, могло потерять атрибуцию.
- `table_partitioning`: секционированный индекс (`CREATE INDEX ...
  GLOBAL PARTITION BY RANGE ...`) больше не приписывается случайной
  несвязанной таблице; добавлена поддержка стратегий `REFERENCE`/`SYSTEM`.
- `insert_all`: окно поиска `INTO` после `INSERT ALL`/`FIRST` расширено —
  не пропускало находку при длинном условии `WHEN`.
- `invisible_column`: `INVISIBLE UNIQUE`/`INVISIBLE PRIMARY KEY` и другие
  inline-ограничения после модификатора теперь тоже флагуются.
- `bulk_collect`: схемный `CREATE TYPE ... EDITIONABLE ... IS TABLE OF`
  больше не дублируется как находка этого детектора.
- Директории: файл, доступный одновременно напрямую и через директорию
  (`schema/ schema/logger.pkb`), больше не учитывается дважды; расширения
  файлов (`.SQL`/`.PKB`) сопоставляются без учёта регистра.
