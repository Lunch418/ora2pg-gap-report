# GAP-090: `IDENTITY(1,1)` disappears entirely on the file-based path

MSSQL feature: `IDENTITY(<seed>, <increment>)` — an auto-increment
column.

## Minimal example

```sql
CREATE TABLE invoices (
    id int IDENTITY(1,1) NOT NULL PRIMARY KEY,
    amount decimal(10,2) NOT NULL
);
```

## ora2pg output, file-based (v25.0, `-M -i schema.sql -t TABLE`)

```sql
CREATE TABLE invoices (
	id integer NOT NULL,
	amount numeric(10,2) NOT NULL
) ;
ALTER TABLE invoices ADD PRIMARY KEY (id);
```

No `serial`, no `GENERATED ... AS IDENTITY`, no separate sequence — the
property vanished entirely.

## Why: same mechanism as GAP-082 and GAP-080

`MSSQL.pm::_get_identities()` (ora2pg 25.0, line 2537) is, like the two
gaps above it, one unconditional live query:

```perl
sub _get_identities
{
	my ($self) = @_;
	my $str = qq{SELECT s.name As SchemaName, t.name As TableName,
	i.name as ColumnName, i.seed_value, i.increment_value, i.last_value
FROM sys.tables t
JOIN sys.identity_columns i ON t.object_id=i.object_id
LEFT OUTER JOIN sys.schemas s ON t.schema_id = s.schema_id};
	...
	my $sth = $self->{dbh}->prepare($str) or $self->logit("FATAL: " . $self->{dbh}->errstr . "\n", 0, 1);
	...
}
```

`$self->{dbh}` is the live DBI handle. There is no branch anywhere in
`MSSQL.pm` that reads `IDENTITY(<seed>, <increment>)` out of the column
definition text itself. On the file-based path there is no database to
query, so this function has nothing to return regardless of what the
column definition says. This mirrors GAP-082's foreign keys and
GAP-080's `AUTO_INCREMENT` start value exactly: three different pieces
of metadata, two dialects, and in every case ora2pg's file-based path
loses it not because the information is missing from the file, it is
right there in the `CREATE TABLE` text, but because that path only ever
asks the live database for it. As with GAP-102, no live SQL Server was
available to confirm the corresponding live-mode export the way GAP-082
and GAP-080 were confirmed against a live MySQL; this is a read of the
source, not a second live export.

## Observed problem

The schema loads without a single error. Verified on live data, real
PostgreSQL 16:

```
=# INSERT INTO invoices (amount) VALUES (9.99);
ERROR:  null value in column "id" of relation "invoices" violates not-null constraint
DETAIL:  Failing row contains (null, 9.99).
```

In SQL Server that exact same `INSERT` succeeds: the server supplies the
`id`.

Worth comparing with the MySQL side of the same ora2pg: there
`AUTO_INCREMENT` is correctly turned into `serial`, and only the
counter's start value is lost (GAP-080). Here nothing is left at all.

**Reproducible: YES**, on the file-based path this project scans. Ora2Pg
version: 25.0, PostgreSQL 16. Source dialect: MSSQL (`ora2pg -M`).

## Verdict

**Gap confirmed for file-based input, severity high, failure_stage
runtime.** The stage is runtime: the schema comes up silently and the
error arrives on the first ordinary insert. Fixed by changing the column
to `GENERATED BY DEFAULT AS IDENTITY` (or `serial`) and then setting the
counter to the maximum of the migrated data, or by exporting from a live
connection to the source SQL Server instead of a file, if that access is
available. Implemented:
`ora2pg_gap_report/detectors/mssql_identity_column.py`.
