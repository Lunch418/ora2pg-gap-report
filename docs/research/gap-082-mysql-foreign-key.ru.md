# GAP-082: `FOREIGN KEY` выбрасывается, если `PG_VERSION` оставлен по умолчанию

MySQL/MariaDB feature: внешний ключ, объявляемый в списке столбцов
`CREATE TABLE`.

## Минимальный пример

В том виде, в каком его пишет `mysqldump`:

```sql
CREATE TABLE `customers` (
  `id` int(11) NOT NULL,
  PRIMARY KEY (`id`)
) ENGINE=InnoDB;
CREATE TABLE `orders2` (
  `id` int(11) NOT NULL,
  `customer_id` int(11) NOT NULL,
  PRIMARY KEY (`id`),
  CONSTRAINT `fk_orders_customer` FOREIGN KEY (`customer_id`) REFERENCES `customers` (`id`) ON DELETE CASCADE
) ENGINE=InnoDB;
```

## Вывод ora2pg с ненастроенным `PG_VERSION` (v25.0, `-m -i schema.sql -t TABLE`)

```sql
CREATE TABLE orders2 (
	id integer NOT NULL,
	customer_id integer NOT NULL
) ;
ALTER TABLE orders2 ADD PRIMARY KEY (id);
```

```
WARNING: target PostgreSQL version must be set in PG_VERSION configuration directive. Using default: 11
```

Строк `FOREIGN KEY` во всём сгенерированном файле — ноль (проверено
`grep -c`).

## Два более ранних объяснения, оба неверные

Первая версия этого документа утверждала, что у `-t` в принципе нет
типа экспорта под внешние ключи. Читатель опроверг это живым прогоном
на MariaDB, где `-t TABLE` корректно экспортировал FK через живое
подключение, — это привело ко второй версии: что у файлового входа нет
живого каталога для запроса, а внешние ключи — это метаданные, которые
ora2pg вообще только и делает, что спрашивает у живой базы, поэтому они
теряются именно на файловом пути.

Объяснение выглядело солидно, с исходниками и всем прочим, но второй
читатель не смог его воспроизвести: ни на файловом входе с несколькими
вариантами схемы, ни живым подключением, за пять отдельных попыток.
Повторный запуск точно той же команды `ora2pg -m -i schema.sql -t
TABLE` из примера выше против дефолтного конфига этого проекта в
песочнице воспроизвёл пропажу FK; тот же запуск с добавленным в конфиг
`PG_VERSION 16` — нет. Различитель никогда не был «файл против живой
базы». Это `PG_VERSION`.

## Настоящий механизм, из исходников и с живой базой одновременно

Подтверждено трассировкой в стиле `perl -d` через `lib/Ora2Pg.pm`, а не
только чтением. `_create_unique_keys()` (вызывается для каждой таблицы
с `PRIMARY KEY` или `UNIQUE`, то есть почти для каждой таблицы) содержит
вот это, задуманное только для обнаружения таблиц с partition-by-reference:

```perl
my $reftable = $table;
$reftable = $self->{partitions_list}{"\L$table\E"}{refrtable}
    if (exists $self->{partitions_list}{"\L$table\E"}{refrtable});
```

`exists` на многоуровневом разыменовании хеша — известная ловушка Perl:
проверка `{refrtable}` таким способом молча создаёт
`$self->{partitions_list}{$table} = {}`, даже если `$table` вообще не
партиционирована, просто потому что промежуточный уровень хеша пришлось
материализовать, чтобы проверить финальный ключ. Через несколько строк
та же функция делает:

```perl
next if (!grep(/^$k$/i, @{$self->{partitions_list}{"\L$reftable\E"}{columns}}));
```

что разыменовывает `{columns}` как массив, авто-создавая и его тоже.
После того как `_create_unique_keys()` хоть раз отработала для таблицы,
`partitions_list` навсегда хранит для неё `{ $table => { columns => [] } }`,
партиционирована та таблица когда-либо или нет. Более поздняя очистка
(`delete $self->{partitions_list}{$t} if ($nb == 0)`, считающая
именно ключи хеша) этого не ловит, потому что у `{columns => []}` уже
есть один ключ.

`_create_foreign_keys()` затем для каждого внешнего ключа проверяет,
не выглядит ли целевая таблица партиционированной, прежде чем вывести
ограничение:

```perl
next if ($self->{pg_supports_partition}
    && exists $self->{partitions_list}{lc($desttable)}
    && $self->{pg_version} <= 12);
```

`exists $self->{partitions_list}{lc($desttable)}` теперь истинно для
`customers` — чисто как побочный эффект более раннего случая, — поэтому
`next` срабатывает и внешний ключ молча пропускается, при условии
`$self->{pg_version} <= 12`. `PG_VERSION` по умолчанию равен 11, если
не задан в конфиге, а это ровно то состояние, в котором находится
конфиг, который никто ещё не редактировал. Стоит выставить `PG_VERSION`
в 13 или выше — то же условие `next` становится ложным, случайная запись
в `partitions_list` безвредна, и ограничение появляется в выводе.

Проверено на четырёх комбинациях, файловый вход и живое подключение к
MariaDB, скрещённые с `PG_VERSION` не заданным/11/12 против 13:

| Вход | `PG_VERSION` | Внешний ключ выведен |
|---|---|---|
| файл (`-i schema.sql`) | не задан (11) | нет |
| файл (`-i schema.sql`) | 12 | нет |
| файл (`-i schema.sql`) | 13 | да |
| живое подключение к MariaDB | не задан (11) | нет |

Строка с живым подключением — та самая, что опровергает предыдущую
версию этого документа: при том же дефолтном конфиге живой источник
теряет внешний ключ точно так же, как и файловый вход. Это никак не
связано с тем, каким способом ora2pg получает схему.

`PRIMARY KEY` не затронут, потому что `_get_primary_keys()` строит его
напрямую из метаданных столбцов, собранных раньше, без всякой
зависимости от `partitions_list`.

## Наблюдаемая проблема

При конфиге, в котором `PG_VERSION` никогда явно не выставлялся (или
выставлен в 12 либо ниже), любой экспорт внешнего ключа через этот путь
кода молча исчезает: ошибки нет ни при загрузке, ни потом, схема
поднимается, приложение работает, а ссылочная целостность просто
перестаёт существовать, вместе с каскадными удалениями, если они были.
Файл это или живая база — разницы нет; триггер — конфиг, а не режим
входа.

**Reproducible: YES**, при `PG_VERSION` не заданном или равном 12 либо
ниже. Ora2Pg version: 25.0, PostgreSQL 16. Source dialect: MySQL
(`ora2pg -m`).

## Вердикт

**Gap подтверждён, severity high, failure_stage semantic**, при условии
`PG_VERSION <= 12` (включая незаданное значение по умолчанию). По
классу это ровно то, что README называет «архитектурно значимой
потерей»: гарантия, объявленная в определении объекта, исчезает
бесследно — родственно GAP-066 (`WITH READ ONLY`) и GAP-026 (`READ
ONLY` на таблице). Чинится установкой `PG_VERSION` в реальную целевую
версию PostgreSQL (13 или выше) перед конвертацией; если цель
действительно PostgreSQL ≤12, ограничение приходится восстанавливать
вручную: `ALTER TABLE <таблица> ADD CONSTRAINT <имя> FOREIGN KEY
(<столбцы>) REFERENCES <родитель> (<столбцы>) ON DELETE ...` после
загрузки всех таблиц. Реализовано:
`ora2pg_gap_report/detectors/mysql_foreign_key.py`.
