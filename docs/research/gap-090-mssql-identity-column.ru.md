# GAP-090: `IDENTITY(1,1)` пропадает целиком на файловом пути

MSSQL feature: `IDENTITY(<начало>, <шаг>)` — автоинкрементный столбец.

## Минимальный пример

```sql
CREATE TABLE invoices (
    id int IDENTITY(1,1) NOT NULL PRIMARY KEY,
    amount decimal(10,2) NOT NULL
);
```

## Вывод ora2pg, файловый путь (v25.0, `-M -i schema.sql -t TABLE`)

```sql
CREATE TABLE invoices (
	id integer NOT NULL,
	amount numeric(10,2) NOT NULL
) ;
ALTER TABLE invoices ADD PRIMARY KEY (id);
```

Ни `serial`, ни `GENERATED ... AS IDENTITY`, ни отдельной
последовательности — свойство исчезло целиком.

## Почему: тот же механизм, что в GAP-082 и GAP-080

`MSSQL.pm::_get_identities()` (ora2pg 25.0, строка 2537) — точно такой
же, как у двух gap'ов выше, один безусловный живой запрос:

```perl
sub _get_identities
{
	my ($self) = @_;
	my $str = qq{SELECT s.name As SchemaName, t.name As TableName,
	i.name as ColumnName, i.seed_value, i.increment_value, i.last_value
FROM sys.tables t
JOIN sys.identity_columns i ON t.object_id=i.object_id
LEFT OUTER JOIN sys.schemas s ON t.schema_id = s.schema_id};
	...
	my $sth = $self->{dbh}->prepare($str) or $self->logit("FATAL: " . $self->{dbh}->errstr . "\n", 0, 1);
	...
}
```

`$self->{dbh}` — живой хендл DBI. Нигде в `MSSQL.pm` нет ветки, которая
читала бы `IDENTITY(<начало>, <шаг>)` из текста определения столбца. На
файловом пути базы, которую можно спросить, нет, поэтому функции
нечего вернуть, независимо от того, что написано в определении столбца.
Это в точности повторяет историю с внешними ключами из GAP-082 и
стартовым значением автоинкремента из GAP-080: три разных вида
метаданных, два диалекта, и в каждом случае файловый путь ora2pg теряет
их не потому, что этой информации нет в файле, она прямо в тексте
`CREATE TABLE`, а потому что этот путь вообще никогда не спрашивает у
живой базы. Живого SQL Server под рукой не было, чтобы подтвердить
соответствующий живой экспорт так же, как это сделано для GAP-082 и
GAP-080; это чтение исходного кода, а не второй живой экспорт.

## Наблюдаемая проблема

Схема загружается без единой ошибки. Проверено на живых данных,
реальный PostgreSQL 16:

```
=# INSERT INTO invoices (amount) VALUES (9.99);
ERROR:  null value in column "id" of relation "invoices" violates not-null constraint
DETAIL:  Failing row contains (null, 9.99).
```

В SQL Server ровно тот же `INSERT` проходит: значение `id` выдаёт
сервер.

Стоит сравнить с MySQL-стороной того же ora2pg: там `AUTO_INCREMENT`
корректно превращается в `serial`, и теряется только стартовое значение
счётчика (GAP-080). Здесь не остаётся ничего.

**Reproducible: YES**, на файловом пути, который сканирует этот проект.
Ora2Pg version: 25.0, PostgreSQL 16. Source dialect: MSSQL (`ora2pg -M`).

## Вердикт

**Gap подтверждён для файлового входа, severity high, failure_stage
runtime.** Стадия именно runtime: схема поднимается молча, ошибка
приходит на первой обычной вставке. Чинится заменой типа столбца на
`GENERATED BY DEFAULT AS IDENTITY` (или `serial`) с последующей
установкой счётчика по максимуму перенесённых данных, либо экспортом
через живое подключение к исходному SQL Server вместо файла, если
такой доступ есть. Реализовано:
`ora2pg_gap_report/detectors/mssql_identity_column.py`.
