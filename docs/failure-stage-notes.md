# failure_stage: заметки по пробному запуску

Это не публичная документация фичи (та часть, что нужна пользователю, —
`--explain`'s "Когда ломается" и `gap_registry.py`'s собственный docstring
поля). Это внутренние заметки по решению из `ROADMAP.md`: "начать с
малого, на 5-10 gap'ов, если модель нормально ложится — раскатить на все
37". Здесь — что именно проверялось, и что из этого вышло.

## Что проверялось

Гипотеза: у каждого gap'а есть конкретный момент в пайплайне
Oracle → ora2pg → PostgreSQL, когда проблема впервые становится реально
видна — не просто severity ("high"/"medium"), а именно *когда конкретно
кто-то это заметит*. Четыре стадии: `conversion` / `deployment` /
`runtime` / `semantic` (определения — в `gap_registry.py`, рядом с
`FAILURE_STAGES`).

Размечено 10 из 37 gap'ов, **только** там, где собственный
research-документ gap'а (`docs/research/gap-*.md`, раздел "Наблюдаемая
проблема") уже явно называет момент отказа — ничего не досочинялось.

## Результат

| Стадия | Кол-во | GAP'ы |
|---|---|---|
| `deployment` | 3 | 021, 028, 031 |
| `runtime` | 2 | 022, 030 |
| `semantic` | 5 | 004, 015, 026, 033, 037 |
| `conversion` | 0 | — |

## Что выяснилось (важно для решения о полном раскате)

1. **`conversion` как стадия ни разу не понадобилась в этой выборке.**
   Даже там, где у `ora2pg` есть собственный сигнал в момент конвертации
   (`context_object`, `materialized_view_log`, `collection_type` — все
   три оставляют `[DEBUG] unhandled line` в логе), реальный момент, когда
   проблема *становится видна без специально включенного DEBUG-уровня* —
   либо `deployment` (для `collection_type` — там ещё и DDL падает
   отдельно, это и есть его стадия), либо вообще никогда (`context_object`
   — DEBUG-строка есть, но ничего дальше не падает, реальная стадия —
   `semantic`). То есть DEBUG-сигнал при конвертации — это отдельная,
   более тонкая характеристика ("есть ли вообще след в логе ora2pg"), не
   совпадающая с failure_stage напрямую. Решение: не путать их в одном
   поле. `conversion` как значение остаётся в `FAILURE_STAGES` (может
   понадобиться для будущего gap'а, где ora2pg сам явно падает с ошибкой
   при конвертации — такого пока в реестре нет), но по факту это,
   возможно, самая редкая категория из четырёх, а не одна из основных.

2. **`compile` как отдельная стадия не нужна вообще.** Изначальная
   идея (из брейншторма пользователя) — 5 стадий, включая `compile`.
   Но `ora2pg`'s собственный сгенерированный дамп сам ставит
   `SET check_function_bodies = false` в начале (подтверждено минимум в
   10 research-документах, не только в размеченных 10 — см.
   `grep -rn check_function_bodies docs/research/`). Из-за этого
   PostgreSQL не проверяет тело функции/процедуры/триггера на синтаксис
   в момент `CREATE` — только при первом реальном вызове. То есть
   "compile-time" ошибки в духе Oracle (объект уходит в `INVALID` сразу
   при компиляции) в реальности всегда становятся `runtime`-ошибками при
   миграции через `ora2pg`. Решение: `compile` из `FAILURE_STAGES`
   исключён — не потому что забыли, а потому что для этого конкретного
   инструмента (конкретно `ora2pg`'s дамп, а не PostgreSQL вообще) такой
   стадии не существует.

3. **Одного поля недостаточно для некоторых gap'ов, но и не нужно
   усложнять.** `autonomous_tx` не помещается ни в одну стадию — его
   находка не о форме кода, а о недооценке стоимости в
   `SHOW_REPORT`. Решение: поле остаётся `None`, как и для
   `verification.py`'s `NOT_VERIFIABLE` по той же причине для того же
   детектора — не выдумывать пятую "N/A"-подобную стадию ради одного
   исключения, когда `None` уже значит именно это.

## Рекомендация по полному раскату (37/37)

Модель проверку прошла: 3 из 4 стадий реально понадобились на
разнообразной выборке, определения не пришлось переписывать по ходу,
`--explain`/`doctor.py`-интеграция работает без сюрпризов. Стоит
раскатывать на оставшиеся 27 gap'ов — по одному, по тому же принципу
(значение берётся из собственного research-документа gap'а, не
придумывается), а не одним большим коммитом на глаз.

Отдельный вопрос, который раскат должен решить попутно: стоит ли
`failure_stage` выводить не только в `--explain`, но и в основном отчёте
(`terminal_report.py`/JSON/HTML/SARIF) — это уже требует менять
публичную JSON Schema (`schemas/report.schema.json`), то есть более
серьёзное, версионируемое обязательство, чем просто внутреннее поле
реестра. Решение сознательно отложено до момента, когда все 37 будут
размечены — до этого расширять публичный формат отчёта под ещё неполные
данные было бы преждевременным обязательством.
