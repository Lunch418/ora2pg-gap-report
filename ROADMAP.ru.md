# Roadmap

Этот документ фиксирует полное видение проекта — куда он может расти,
если станет реально нужным инструментом, а не проектом на выходные.
Никаких сроков нет: пункты ниже — не план на квартал, а backlog,
из которого пункты вынимаются только когда для них появляется
подтверждённая причина (реальный пользователь, реальный issue, реальная
боль). См. правило в конце документа.

Статус актуален на v0.6.0 (2026-08-18).

## Как читать этот список

Три раздела:

- **Уже есть** — то, что многие ожидали бы увидеть тут как "будущую
  фичу", но это уже реализовано, просто не всегда очевидно из README.
- **Ближайшее** — небольшие, недорогие шаги, которые доводят уже
  существующие возможности до конца или устраняют реальный, уже
  видимый разрыв.
- **Backlog** — крупные направления. Они не отсортированы по приоритету
  и не являются обещанием. Каждое ждёт своего триггера: конкретный
  пользователь, конкретный issue, конкретный кейс, который текущий
  инструмент не покрывает.

## Уже есть

Ядро "evidence-based verification layer" — то, ради чего вообще
затевался проект — уже стоит:

- **Verification, а не догадки**: `--verify` сравнивает конвертированный
  PostgreSQL-код с pre-migration снапшотом (`--baseline`) на уровне
  детекторов и даёт `STILL_PRESENT` / `NOT_DETECTED` / `NOT_VERIFIABLE`
  — `NOT_VERIFIABLE` первым классом, а не спрятан и не выдаётся за
  "исправлено".
- **Baseline / diff**: `--save` + `--baseline` — `NEW` / `RESOLVED` /
  `UNCHANGED` между прогонами.
- **CI-гейт**: `--fail-on high|medium|low` — код возврата 1, если есть
  находка нужной серьёзности, независимо от `--severity`/`--object`
  фильтров вывода.
- **Нативная интеграция с GitHub/GitLab code scanning**: `--format
  sarif` — SARIF 2.1.0. Через `github/codeql-action/upload-sarif`
  GitHub сам рисует находки построчно прямо в PR — не нужен свой бот
  или Action для этого (см. "Ближайшее" — не хватает только
  задокументированного примера).
- **Evidence pages**: `--explain GAP-NNN` + `docs/research/gap-*.md`
  (47 штук) — минимальный пример, реальный вывод `ora2pg`, что
  происходит в PostgreSQL, обоснование severity.
- **Reproduce для CONNECT BY**: `--check-connect-by` реально прогоняет
  установленный `ora2pg` и проверяет сгенерированный `WITH RECURSIVE`
  на конкретный известный баг с `LEVEL` — не гипотеза, а
  воспроизведённый факт.
- **HTML/JSON/CSV/Markdown отчёты**: `--format html` — самодостаточная
  страница без внешних ресурсов, для показа не-инженеру.
- **Guardian реестра**: `scripts/doctor.py` — ловит расхождение между
  кодом детекторов, `gap_registry.py`, `verification.py`,
  research-документами и тестами. Часть CI.
- **i18n**: RU/EN на уровне UI и текстов находок (`--lang`,
  `--set-lang`), README и README.ru.md.
- **Оффлайн-установка**: `scripts/build_offline_bundle.py` +
  автоматическая сборка бандла в CI на каждый релиз (для closed-network
  окружений — частый случай для Oracle→PostgreSQL миграций).
- **CI-рецепт**: [`docs/ci-integration.md`](docs/ci-integration.ru.md) —
  пайплайн вместе с `ora2pg` (гейт до конвертации, `--check-connect-by`,
  `--verify` после) и пример GitHub Actions workflow, который через
  `--format sarif` + `upload-sarif` даёт находки построчно в PR без
  своего бота или Action.
- **Verification capability matrix**:
  [`docs/verification-capability-matrix.md`](docs/verification-capability-matrix.ru.md)
  — по каждому из 47 gap'ов явно, какой режим верификации у него
  (`verbatim`/`not_verifiable`/`generated_only`) и почему, сверено с
  `VERIFICATION_MODE` в коде построчно (не написано на глаз).
- **`failure_stage`**: на каком этапе gap реально становится заметен —
  `deployment`/`runtime`/`semantic` (`conversion` определён, но ни разу
  не понадобился — см. `docs/failure-stage-notes.md`). Раскатано на все
  47 gap'ов (кроме двух намеренных исключений — находки не о форме кода,
  а о недооценке `--estimate_cost`), `doctor.py` требует полное покрытие.
  Показывается не только в `--explain`, но и в основном отчёте: колонки
  в `--format markdown`/`html`, поля в `--format json`/`csv`, `properties`
  на правиле в SARIF, строка "GAP-NNN · стадия" в панели пояснений
  терминального вывода, поля в `--save`-снапшотах. `schemas/report.
  schema.json`/`schemas/baseline.schema.json` обновлены и синхронно.
- **`--tui`**: интерактивный экран на `textual` (опциональный extra
  `[tui]`, не в базовой установке) — выбор пути мышью/клавиатурой вместо
  флагов, сканирование по кнопке, клик по находке открывает полное
  объяснение с `GAP-NNN`/`failure_stage`. Первая версия намеренно узкая:
  только сканирование и просмотр, без `--save`/`--baseline`/`--verify`/
  `--check-connect-by` изнутри и без множественного выбора путей — см.
  backlog ниже про расширение.

## Ближайшее

Небольшие, недорогие шаги, которые докручивают уже существующее:

- Explain/evidence-документы (`docs/research/gap-*.md`) написаны для
  контрибьюторов, не для конечного пользователя — можно проверить,
  насколько они читаемы без контекста кодовой базы.

## Backlog (без порядка, без сроков)

Идеи ниже разной степени зрелости — от "почти готово выделить" до
"нужен реальный кейс, чтобы понять, нужно ли это вообще". Каждая ждёт
триггера.

### Понимание риска
- Отдельная категория "тихая потеря" (silent loss) — по факту уже
  закрыта как часть `failure_stage`: значение `semantic` ровно про
  это (ошибки не будет никогда, поведение просто тихо отличается).
  Отдельная таксономия сверх `failure_stage` пока не требуется.

### Интерактивный режим
- `--tui`: множественный выбор путей пока только через дерево ("Add to
  selection" по одному) — drag-select/чекбоксы в самом дереве не
  реализованы, если понадобится при реальном использовании.

### Workflow миграции
- `waiver`/suppression с явным сроком действия — принятый и
  задокументированный риск, а не забытый.
- Migration checklist, генерируемый из находок конкретного прогона.
- Migration recipes: `docs/recipes/` — по каждому классу проблем
  (не по каждому detector'у) отдельный документ "проблема → паттерн
  миграции → альтернативы", отдельно от evidence-документов
  детекторов.

### Экосистема
- Официальный пример GitHub Action (обёртка над CLI + SARIF, не
  отдельный сервис).
- `--annotate`: безопасная вставка комментариев прямо в конвертированный
  SQL-файл рядом с находками (`-- ora2pg-gap-report: GAP-023, see ...`)
  — ничего не переписывает, не меняет валидность файла, просто кладёт
  контекст туда, где разработчик и так откроет файл.

### Доверие и прозрачность
- Version compatibility matrix: против каких версий `ora2pg` реально
  проверялось каждое поведение.
- Публичные метрики без фальшивой точности: например "у каждого
  зарегистрированного GAP есть regression-фикстура" — но только пока
  это утверждение реально верно (проверяется `doctor.py`).

## Правило приоритизации

**Ни одна фича не берётся в работу без реальной причины.** Реальная
причина — это конкретный issue, конкретный пользователь, конкретный
воспроизводимый кейс, который сегодняшний инструмент не покрывает.
Не "было бы круто", не "по аналогии с большим enterprise-инструментом".

Это тот же принцип, что уже действует для самих детекторов
(`CONTRIBUTING.md`): находка не попадает в реестр, пока не
подтверждена на практике. Roadmap работает так же — пункт не
попадает в разработку, пока для него нет практического подтверждения.
