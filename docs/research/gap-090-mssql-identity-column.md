# GAP-090: `IDENTITY(1,1)` disappears entirely

MSSQL feature: `IDENTITY(<seed>, <increment>)` — an auto-increment
column.

## Minimal example

```sql
CREATE TABLE invoices (
    id int IDENTITY(1,1) NOT NULL PRIMARY KEY,
    amount decimal(10,2) NOT NULL
);
```

## ora2pg output (v25.0, `-M -t TABLE`)

```sql
CREATE TABLE invoices (
	id integer NOT NULL,
	amount numeric(10,2) NOT NULL
) ;
ALTER TABLE invoices ADD PRIMARY KEY (id);
```

No `serial`, no `GENERATED ... AS IDENTITY`, no separate sequence — the
property vanished entirely.

## Observed problem

The schema loads without a single error. Verified on live data, real
PostgreSQL 16:

```
=# INSERT INTO invoices (amount) VALUES (9.99);
ERROR:  null value in column "id" of relation "invoices" violates not-null constraint
DETAIL:  Failing row contains (null, 9.99).
```

In SQL Server that exact same `INSERT` succeeds: the server supplies the
`id`.

Worth comparing with the MySQL side of the same ora2pg: there
`AUTO_INCREMENT` is correctly turned into `serial`, and only the
counter's start value is lost (GAP-080). Here nothing is left at all.

**Reproducible: YES.** Ora2Pg version: 25.0, PostgreSQL 16. Source
dialect: MSSQL (`ora2pg -M`).

## Verdict

**Gap confirmed, severity high, failure_stage runtime.** The stage is
runtime: the schema comes up silently and the error arrives on the first
ordinary insert. Fixed by changing the column to `GENERATED BY DEFAULT AS
IDENTITY` (or `serial`) and then setting the counter to the maximum of
the migrated data. Implemented:
`ora2pg_gap_report/detectors/mssql_identity_column.py`.
