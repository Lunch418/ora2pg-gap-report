# Step 0: baseline ora2pg SHOW_REPORT — что уже есть "из коробки"

Дата: 2026-08-14
Автор: research-агент (в рамках Задачи 0 проекта `ora2pg-gap-report`)

Цель документа — эмпирически (и там, где эмпирика невозможна — по исходному
коду) выяснить, что режим `SHOW_REPORT` открытого `ora2pg` уже репортит по
пяти заявленным классам "плохо переносимых" конструкций, прежде чем
проектировать детекторы поверх него. Итог: гипотеза **частично** подтверждается,
но не в той форме, в которой была сформулирована изначально — детали ниже.

### Офлайн-режим: что можно и что нельзя

Важно для целевой аудитории (закрытые контуры без прямого доступа к боевой
Oracle):

- **Можно офлайн** (`-i file.sql`, без `ORACLE_DSN`, без `DBD::Oracle`,
  только `perl` + модуль `DBI`): экспорт/оценка стоимости отдельных типов
  объектов — `PACKAGE`, `TRIGGER`, `FUNCTION`, `PROCEDURE`, `VIEW`, `TYPE`,
  `QUERY` и др., если на вход подать файл с DDL/PL-SQL текстом этого объекта.
  Именно так был получен весь эмпирический вывод в этом отчёте.
- **Нельзя офлайн**: сам `SHOW_REPORT` как единый агрегированный отчёт.
  Причина — не искусственное ограничение, а архитектурная: `_show_infos`
  для типа `SHOW_REPORT` дергает `_get_objects()`, `_get_version()`,
  `_get_database_size()`, `_tables()`, `_get_views()`, `_get_dblink()`,
  `_get_job()`, `_synonyms()`, `_encrypted_columns()` и т.д. — то есть
  напрямую строит SQL и читает `$self->{dbh}` (см., например,
  `Ora2Pg/Oracle.pm::_get_objects()`: `SELECT OBJECT_NAME,OBJECT_TYPE,STATUS
  FROM ALL_OBJECTS ...` через `$self->{dbh}->prepare(...)`). Общая проверка
  в `Ora2Pg.pm` (~строка 1834–1840) явно требует либо `input_file`, либо
  `ORACLE_DSN` для *любого* типа экспорта, но для `SHOW_REPORT` `input_file`
  не помогает — код репорта всё равно обращается к `$self->{dbh}` напрямую и
  упадёт с ошибкой уровня DBI, если реального подключения нет. При запуске
  `-t SHOW_REPORT` без `ORACLE_DSN` и без входного файла получаем:

  ```
  FATAL: you must set ORACLE_DSN in ora2pg.conf or use a DDL input file.
  ```

  Формулировка ошибки вводит в заблуждение — она предполагает, что
  "DDL input file" покрывает и `SHOW_REPORT`, но по факту это верно только
  для типов объектов, а не для самого репорта целиком. Мы это **не смогли
  обойти** и не пытались долго биться (в соответствии с инструкцией) —
  зафиксировано как находка №1: **`SHOW_REPORT` принципиально требует живого
  DBI-подключения к Oracle/MySQL/MSSQL и не имеет офлайн-режима**, несмотря
  на то, что отдельные типы объектов (включая PACKAGE, откуда берётся
  большая часть интересующих нас конструкций) вполне поддерживают файловый
  вход. Это значит, что наш инструмент, если он должен работать в
  air-gapped контуре с уже выгруженным DDL-дампом (как заявлено в
  README проекта), **не может** просто "запустить SHOW_REPORT и дополнить
  его выводом" в offline-сценарии — придётся либо (a) требовать live-доступ
  к Oracle только для этапа baseline-сверки, либо (b) воспроизводить
  собственным кодом ту часть SHOW_REPORT, которая реально нужна
  (`estimate_cost()` + `%UNCOVERED_SCORE`), на файловом входе — благо это
  ровно тот путь, который мы использовали для тестов ниже, и он реально
  работает офлайн.

## Результаты по 5 классам конструкций

### 1. CREATE PACKAGE / CREATE PACKAGE BODY

**Подтверждено запуском.** Ora2pg **умеет** парсить и конвертировать
пакеты из файла офлайн — никакого краха или отказа. На `logger.pkb`
(≈3300 строк, десятки функций/процедур) и `file_util_pkg.pkb`:

```
[...] 1/1 packages (100.0%) generating logger
```

— пакет успешно разбит на отдельные функции/процедуры,
каждая конвертирована в `CREATE OR REPLACE FUNCTION ... LANGUAGE plpgsql`,
глобальные переменные пакета вынесены в `global_variables.conf`
(GUC-эмуляция через `current_setting`/`set_config`), сгенерирован блок
`-- Detailed cost per function: ...` с оценкой по каждой функции.

`SHOW_REPORT` (по коду) для `PACKAGE BODY` даёт даже более грубую сводку,
чем прямой `-t PACKAGE --estimate_cost`: только суммарный
`cost_value` по всем функциям пакета плюс текстовый `detail` вида
`имя_функции: cost\n` без разбивки по ключевым словам на уровне
самого `SHOW_REPORT`-вывода в консоли/CSV/JSON (разбивка по ключевым словам
хранится в `%report_info{full_package_details}`, но попадает в
финальный отчёт только в `--dump_as_html`/подробный текстовый режим, не в
базовые CSV/JSON — см. `_show_report`).

**Вывод:** сам факт "PACKAGE это пакет" ora2pg распознаёт и переносит
корректно в подавляющем большинстве случаев (парсер справляется с
реальным, не игрушечным кодом). Заявленный тезис "PACKAGE не переносится
корректно" **не подтверждается** в таком общем виде — базовая структура
пакета (спецификация, тело, функции/процедуры, глобальные переменные)
конвертируется. Проблема не в самом факте CREATE PACKAGE, а в **содержимом**
пакетов — в частности в том, что происходит с `PRAGMA
AUTONOMOUS_TRANSACTION` и обращениями к `DBMS_*/UTL_*` **внутри** пакета
(см. ниже — и там как раз обнаружен неочевидный, but real, gap).

### 2. PRAGMA AUTONOMOUS_TRANSACTION

Это самая интересная и самая контринтуитивная находка отчёта.

**У ora2pg ЕСТЬ настоящая, нетривиальная логика конвертации этой прагмы**
(`lib/Ora2Pg.pm`, ~строка 15874, и `lib/Ora2Pg/PLSQL.pm`, ~строка 848–851):
по умолчанию (`AUTONOMOUS_TRANSACTION` конфиг-опция включена, `= 1`) ora2pg
генерирует **dblink-обёртку**: исходная функция/процедура переименовывается
в `<имя>_atx`, `COMMIT` внутри неё убирается (в PL/pgSQL функции `COMMIT`
запрещён), а вызывающий код получает функцию-прокси, которая через
`dblink()` вызывает `<имя>_atx` в отдельном соединении — то есть реально
эмулирует автономность транзакции. Это подтверждено живым запуском на
`logger.pkb`: для каждой из процедур с `pragma autonomous_transaction;`
(например, `logger.save_global_context`, `logger.log_apex_items`,
`logger.purge`, `logger.purge_all`) в выводе реально появляется:

```sql
-- dblink wrapper to call function logger_save_global_context as an autonomous transaction
CREATE EXTENSION IF NOT EXISTS dblink;
...
	-- Change this to reflect the dblink connection string
	v_conn_str := ...
	v_query := 'CALL logger_save_global_context_atx ( ... )';
	PERFORM * FROM dblink(v_conn_str, v_query) AS p (ret boolean);
...
CREATE OR REPLACE PROCEDURE logger_save_global_context_atx (...) AS $body$
...
```

Это реальная, работоспособная (хоть и требующая ручной правки строки
подключения и включения `dblink`) стратегия конвертации — **не** просто
предупреждение в комментарии. Значит тезис "PRAGMA AUTONOMOUS_TRANSACTION
не переносится" в буквальном смысле **неверен**: ora2pg переносит её,
причём осмысленно.

**НО.** При этом обнаружен конкретный, воспроизводимый баг/слепое пятно в
собственной системе **оценки стоимости** (`estimate_cost`/`%UNCOVERED_SCORE`,
на которой основана детализация `SHOW_REPORT`), причём именно в пакетах:

- `%UNCOVERED_SCORE` содержит `'PRAGMA' => 3` — вес, который *должен* бы
  добавляться при виде `PRAGMA AUTONOMOUS_TRANSACTION`.
- Но для функций **внутри package body** (это касается и `SHOW_REPORT`
  — `Ora2Pg.pm:18340`, и прямого `-t PACKAGE --estimate_cost` —
  `Ora2Pg.pm:7275`) стоимость считается только по
  `estimate_cost($self, $infos{$f}{code}, ...)`, где `{code}` — это часть
  текста функции **после** ключевого слова `BEGIN` (см.
  `Ora2Pg/Oracle.pm::_lookup_function`, строка 1620: `($fct_detail{declare},
  $fct_detail{code}) = split(/\bBEGIN\b/i, $plsql, 2);`). А
  `PRAGMA AUTONOMOUS_TRANSACTION;` синтаксически всегда стоит в
  декларативной секции — **до** `BEGIN`, то есть попадает в `{declare}`, а
  не в `{code}`. `{declare}` в `estimate_cost` для пакетных функций/процедур
  просто никогда не передаётся.
- Эмпирически подтверждено: в реальном выводе конвертации `logger.pkb` для
  `logger.save_global_context` (функция, где ora2pg САМ сгенерировал
  dblink-обёртку, то есть точно "увидел" прагму на этапе конвертации)
  итоговая оценка стоимости — `total estimated cost: 6`, разбивка —
  `TEST => 2`, `SIZE => 1`, `DBMS_ => 1 (cost: 3)` — **строки `PRAGMA` в
  разбивке нет вообще**, хотя вес 3 для неё в таблице задан. Это не единичный
  случай — из 9 вхождений `pragma` в `logger.pkb`, ни одно не отражено в
  строке `PRAGMA => N (cost: 3)` ни в одном из отчётов по функциям пакета.

  Для контроля: если то же самое `CONNECT BY` встречается **внутри** тела
  функции пакета (после `BEGIN` — а хеш-запросы всегда там), оно попадает в
  `{code}` и корректно учитывается в стоимости (см. раздел 3 — на нашем
  fixture `hierarchy_demo_pkg` строка `CONNECT BY => 1 (cost: 3)`
  присутствует). Это подтверждает, что причина именно в позиции
  конструкции относительно `BEGIN`, а не в том, что `PRAGMA` как ключевое
  слово вообще не ищется.

**Вывод:** ora2pg реально *конвертирует* `PRAGMA AUTONOMOUS_TRANSACTION`
через dblink-эмуляцию (не "не переносит"), но при этом **систематически
недооценивает трудоёмкость/риск** этой конструкции в `SHOW_REPORT` и в
`--estimate_cost` для пакетных функций — стоимость по этой конструкции
теряется на этапе разбора функции (declare/code split), а не только "не
показана детально". Это конкретный, узкий, легко объяснимый и легко
воспроизводимый пробел — отличная задача для нашего инструмента: (1)
посчитать реальное число `PRAGMA AUTONOMOUS_TRANSACTION` в пакетах (что
`SHOW_REPORT` для пакетов не делает вообще), и (2) объяснить человеку, что
"перенос" здесь на самом деле означает "код будет вызывать другую БД через
`dblink`, с ручной настройкой connection string, что для контура с
жёсткими требованиями к целостности транзакций и к отсутствию сетевых
зависимостей между процедурами может быть неприемлемо" — то есть не просто
цифра, а архитектурное предупреждение, которого `SHOW_REPORT` не даёт в
принципе (он в лучшем случае покажет заниженную цифру, в худшем — не
покажет вообще ничего специфичного для этой конструкции).

### 3. CONNECT BY (иерархические запросы)

**Подтверждено запуском** (на синтетическом, но честно помеченном fixture
`hierarchy_demo_pkg`, обёртке над каноническим Oracle EMP/DEPT-запросом,
внутри реального пакета с `REF CURSOR`). Ora2pg **реально конвертирует**
`START WITH ... CONNECT BY PRIOR ... SYS_CONNECT_BY_PATH` в рабочий
`WITH RECURSIVE`-CTE PostgreSQL:

```sql
WITH RECURSIVE cte AS (
SELECT employee_id,manager_id,1 AS depth,last_name AS org_path
      FROM   employees WHERE employee_id = p_top_employee_id
  UNION ALL
SELECT employee_id,manager_id,(c.level+1) AS depth,c.org_path || '/' || last_name AS org_path
      FROM   employees JOIN cte c ON (c.employee_id = manager_id)
) SELECT * FROM cte;
```

— `LEVEL` превращён в счётчик глубины, `SYS_CONNECT_BY_PATH` — в конкатенацию
строк, `START WITH`/`CONNECT BY PRIOR` — в анкер и рекурсивный JOIN.
Механически это рабочий SQL. Стоимость учтена корректно: `CONNECT BY => 1
(cost: 3)` присутствует в детальном отчёте по функции — потому что запрос
находится в теле функции (после `BEGIN`), в отличие от `PRAGMA` из пункта 2.

Однако конвертация **шаблонная и хрупкая** (это видно прямо из
сгенерированного кода, без необходимости запускать результат на реальном
Postgres): `(c.level+1)` — в CTE нет колонки `level`, это баг подстановки
regex-based конвертера, который просто взял литеральное имя `LEVEL` и не
подставил алиас `depth` из первой ветки `UNION`; сгенерированный SQL в
буквальном виде **не будет работать** без ручной правки (`c.level` нужно
заменить на `c.depth`). Также конвертер не умеет более сложные варианты
`CONNECT BY` — `CONNECT BY NOCYCLE`, множественные условия в `CONNECT BY`,
`ORDER SIBLINGS BY`, `CONNECT_BY_ROOT`, `CONNECT_BY_ISLEAF` — они не
покрыты ни одним регулярным выражением в `PLSQL.pm` (проверено чтением
кода: единственные `CONNECT BY`-специфичные преобразования там — под
базовый `START WITH ... CONNECT BY PRIOR`).

**Вывод:** `CONNECT BY` — единственный из пяти классов, где базовый
`SHOW_REPORT`/`estimate_cost` не занижает, а корректно считает стоимость
(вес 3 за вхождение). Но при этом сама конвертация в `WITH RECURSIVE`
**не безошибочна на практике** (наглядный сгенерированный баг с `LEVEL`/alias)
и **не покрывает** более сложные варианты синтаксиса. `SHOW_REPORT`
сигнализирует только "здесь есть CONNECT BY, это стоит N единиц", но не
говорит, что автоматическая конвертация в принципе может быть некорректной
даже для базового случая — то есть здесь наша добавленная ценность не
"мы обнаруживаем то, что ora2pg не видит вообще", а "мы предупреждаем, что
даже когда ora2pg конвертирует и показывает ненулевую стоимость,
сгенерированный SQL нужно обязательно вручную вычитывать — цена риска выше,
чем предполагает голая цифра".

### 4. Вызовы DBMS_*/UTL_* (DBMS_OUTPUT, DBMS_LOB, UTL_FILE, DBMS_SCHEDULER)

Смешанная картина, подтверждённая и запуском, и чтением кода:

- **`DBMS_OUTPUT.put_line/put/new_line`** — есть целевая конвертация:
  regex в `PLSQL.pm` (~строка 976) переписывает вызовы в
  `PERFORM`-обёртку/`raise_output()`-хелпер (по факту — сообщение через
  `RAISE NOTICE`-подобный механизм). `DBMS_OUTPUT.ENABLE` просто
  комментируется. Специальный вес в `%UNCOVERED_SCORE` —
  `'DBMS_OUTPUT.put' => 1` — ниже общего `DBMS_ => 3`, то есть эта
  конкретная, в целом безобидная конструкция уже выделена и оценена ниже
  остальных `DBMS_*`.
- **`DBMS_LOB`** — только 2 функции из десятков имеют прямую замену:
  `DBMS_LOB.GETLENGTH` → `octet_length`, `DBMS_LOB.SUBSTR(...)` →
  `substr(...)` (с перестановкой аргументов). Всё остальное (`READ`,
  `WRITE`, `LOADFROMFILE`, `COMPARE`, `INSTR`, `APPEND`, `CREATETEMPORARY`
  и т.д. — а в `file_util_pkg.pkb`/`sql_util_pkg.pkb` используется именно
  это) остаётся без изменений и просто попадает в общий счётчик `DBMS_`
  (вес 3), без указания, какая именно из ~20 функций `DBMS_LOB`
  использована и какие из них вообще не имеют осмысленного эквивалента в
  PostgreSQL без `orafce`/ручного переписывания на large objects.
- **`UTL_FILE`** — **нет вообще никакой специальной конвертации** (проверено
  по коду — единственное упоминание `UTL_FILE` в `PLSQL.pm` — это строка
  подсчёта для cost estimation). 21 вызов `UTL_FILE.*` в
  `file_util_pkg.pkb` (реальный код: `fopen`, `put_line`,
  `get_line`, `fclose`, режимы `w`/`r`/wb) остаются в выводе как есть —
  синтаксис, которого в PostgreSQL не существует без `orafce`. Учтены
  только генерическим бакетом `UTL_ => 5 (cost: 3)` / `UTL_ => 6 (cost: 3)`
  на функцию — без указания, что конкретно `fopen`/`put_line`/`fclose`
  использованы и что нужно либо подключать `orafce`, либо переписывать
  логику через `pg_read_file`/COPY/large objects — принципиально разные
  архитектурные решения с разной трудоёмкостью, а ora2pg показывает всё
  под одной обезличенной меткой `UTL_`.
- **`DBMS_SCHEDULER`** — как *вызов внутри процедуры* (не как отдельный
  объект `JOB`) не упоминается в `PLSQL.pm`/`Ora2Pg.pm` вообще нигде,
  кроме общего `DBMS_\w` regex в `estimate_cost` (который его, конечно,
  тоже поймает как `DBMS_` с весом 3, потому что попадает под общий
  паттерн `DBMS_\w`) — но никакой специфичной для планировщика логики или
  предупреждения нет. Отдельно, для объектов типа `JOB` (то есть
  запланированных задач, созданных как `CREATE JOB`/через `DBMS_SCHEDULER`
  на уровне схемы, а не вызовов внутри произвольного кода) `SHOW_REPORT`
  **действительно** даёт содержательный, специфичный комментарий (это
  подтверждено чтением кода, `Ora2Pg.pm:18441`): `"Job are not exported.
  You may set external cron job with them."` — то есть здесь для целого
  класса объектов SHOW_REPORT уже даёт то, что и предполагалось от нашего
  инструмента (текстовое пояснение поверх цифры), но это касается только
  первоклассных `JOB`-объектов, а не произвольных `DBMS_SCHEDULER.*`-вызовов
  из процедурного кода.

**Вывод:** гипотеза "DBMS_*/UTL_* не переносятся корректно" в целом
**подтверждается**, но не как бинарная "видит/не видит" история — правильнее
сказать: `SHOW_REPORT` **видит факт использования** (генерический счётчик
`DBMS_`/`UTL_`, вес 3 за каждое вхождение), но **не различает** внутри этого
счётчика ни (а) какая конкретно функция/пакет использована, (б) есть ли для
неё вообще целевая замена в ora2pg (для 2 функций `DBMS_LOB` и всего
`DBMS_OUTPUT` — есть; для `UTL_FILE` целиком и подавляющего большинства
`DBMS_LOB` — нет), ни (в) какого рода архитектурное решение потребуется
(в PL/pgSQL runtime? в `orafce`? переписать логику?). Именно здесь у
`SHOW_REPORT` самое большое расстояние между "что он говорит" (плоское
число) и "что нужно знать инженеру, чтобы спланировать работу" — это,
похоже, наиболее убедительная из пяти зон для нашего инструмента, при
условии что мы конкретизируем именно до уровня "какая функция из какого
пакета вызвана и есть ли для неё готовая замена в ora2pg", а не
переизобретаем сам факт "здесь используется DBMS_*".

### 5. COMPOUND TRIGGER (составные триггеры)

**Самая сильная, наиболее однозначно подтверждённая находка отчёта**, и
единственная, где реальный запуск дал бинарный "не найдено" результат, а
не "найдено, но неточно".

На реальном файле с синтаксически корректным `COMPOUND TRIGGER`
(`Apress/modern-oracle-database-programming`, `tr_constructors_cti`, все 4
секции — `BEFORE STATEMENT`, `BEFORE EACH ROW`, `AFTER EACH ROW`, `AFTER
STATEMENT`):

```
ora2pg -t TRIGGER -i compound_trigger_apress.sql --estimate_cost ...
[...] 0/0 triggers (100.0%) end of output.
-- Nothing found of type TRIGGER
```

Контрольный запуск на классическом простом триггере (`BEFORE INSERT OR
UPDATE ... FOR EACH ROW BEGIN ... END`) из того же самого прогона —
`1/1 triggers`, корректная конвертация в `CREATE FUNCTION` +
`CREATE TRIGGER`. То есть это не проблема окружения/настройки — это
конкретный, воспроизводимый провал парсера **именно** на составных
триггерах.

**Причина (по коду):** `read_trigger_from_file()`
(`Ora2Pg.pm`, ~строка 3868) разбирает тело триггера двумя жёсткими regex,
оба из которых требуют, чтобы сразу после `ON <table>` шло `FOR EACH
ROW/STATEMENT`, затем опционально `WHEN (...)`, а затем непосредственно
`BEGIN`/`DECLARE`. Синтаксис `COMPOUND TRIGGER` в принципе не содержит ни
`FOR EACH ROW` на верхнем уровне (тайминг задаётся отдельно в каждой из
четырёх секций), ни единственного `BEGIN` сразу после объявления — вместо
этого идёт `COMPOUND TRIGGER`, декларативная секция, затем 4 именованных
блока `BEFORE STATEMENT IS ... END BEFORE STATEMENT;` и т.д. Ни один из
regex-ов не рассчитан на эту форму → триггер целиком выпадает из
результата, **без единого предупреждения** ("Nothing found" — это
стандартное сообщение "файл пуст", а не "не смог распарсить").

**Важная оговорка (не подтверждено запуском, только по коду):** в
живом режиме (подключение к Oracle, не файловый вход) объект-триггер как
таковой **будет** учтён в счётчике `SHOW_REPORT` `TRIGGER: number/invalid`
— потому что этот счётчик берётся из каталога `ALL_OBJECTS`/`ALL_TRIGGERS`
Oracle напрямую (`_get_objects()`, `_get_triggers()`), а не через
файловый regex-парсер, и Oracle пометит валидный `COMPOUND TRIGGER` как
`VALID`. То есть **число объектов в SHOW_REPORT не покажет проблему** —
компаунд-триггер будет выглядеть как один обычный валидный триггер. Мы не
смогли проверить в этой песочнице (нет живого Oracle), но по коду
`export_trigger()` (`Ora2Pg.pm:5975+`) применяет к телу триггера,
полученному из `TRIGGER_BODY` через ту же самую DB-колонку, ряд
преобразований (`s/\s*EACH ROW//is`, разбор `trig->[1]`/`trig->[2]` как
"тип BEFORE/AFTER/INSTEAD OF" + "событие INSERT/UPDATE/DELETE"), которые
несовместимы со значением `TRIGGER_TYPE = 'COMPOUND'` и телом,
начинающимся с `COMPOUND TRIGGER` — то есть по всей структуре кода крайне
вероятно, что и в live-режиме реальная конвертация тела компаунд-триггера
либо давала бы синтаксически некорректный PL/pgSQL, либо тихо портила бы
логику (нет проверки "это compound trigger, обработай иначе" нигде в
кодовой базе — grep по `COMPOUND` в `lib/` вне geometry-модуля не даёт
ничего). Это явно помечено здесь как вывод по чтению кода, не
подтверждённый живым запуском.

**Вывод:** гипотеза **полностью подтверждается**, причём даже сильнее, чем
заявлено: `COMPOUND TRIGGER` — это не "переносится некорректно", это
**полностью выпадает** из файлового режима ora2pg без единого
предупреждения, и по коду похоже, что и в live-режиме результат будет либо
испорченным, либо синтаксически неверным телом функции-триггера, при этом
метрика "number of triggers / invalid triggers" в `SHOW_REPORT` **не
покажет вообще ничего подозрительного**, потому что она берётся из
каталога Oracle, а не из попытки конвертации. Это ровно тот тип разрыва,
который человек, полагающийся на голые цифры `SHOW_REPORT`, не заметит,
пока не увидит пустой/сломанный вывод после реальной конвертации — то есть
именно тот сценарий "постфактум, когда уже сломалось в проде", который
описан в README проекта как исходная проблема.

## Подтверждается ли исходная гипотеза?

**Частично, и в более конкретной форме, чем сформулировано изначально.**

Исходная рамка ("SHOW_REPORT не видит эти 20% вообще, наш инструмент их
обнаруживает") **неточна**: `SHOW_REPORT` **видит** факт использования всех
пяти конструкций на уровне ключевых слов (кроме COMPOUND TRIGGER в файловом
режиме, где происходит полный провал парсинга) и даже в трёх случаях из
пяти (PACKAGE, CONNECT BY, часть DBMS_*) реально пытается или полностью
успешно выполняет конвертацию — не просто предупреждает.

Более точная и, что важно, **подтверждённая экспериментально** рамка для
реальной добавленной ценности инструмента:

1. **COMPOUND TRIGGER** — единственный случай настоящего "слепого пятна"
   в буквальном смысле слова: не видно вообще ничего, ни числа, ни
   предупреждения (в файловом режиме — подтверждено; в live-режиме,
   по коду, число объекта будет, но без указания, что это compound-триггер
   и что конвертация, скорее всего, провалится).
2. **PRAGMA AUTONOMOUS_TRANSACTION** — не "не видно", а **специфичный,
   воспроизводимый баг недооценки трудоёмкости** именно для функций внутри
   пакетов (самый частый случай на практике — большинство autonomous
   transaction процедур живёт именно в пакетах, как в нашем примере с
   Logger), плюс отсутствие предупреждения о том, что "перенесённый" код
   на самом деле требует `dblink`, отдельного соединения и ручной настройки
   connection string — то есть архитектурного решения, а не просто синтаксиса.
3. **DBMS_*/UTL_*** — не "не видно", а **обезличено**: есть число, нет
   идентификации конкретной функции/пакета и того, покрыта ли она у ora2pg
   готовой заменой или нет.
4. **CONNECT BY** — не "не видно", а **недооценён риск**: цифра есть и
   корректна, конвертация происходит, но может быть тихо неверной даже в
   базовом случае — просто предупреждения об этом riске нет.
5. **PACKAGE как таковой** — гипотеза не подтверждается: структура пакета
   переносится нормально, детектор "здесь есть пакет — это проблема" сам
   по себе не нужен; ценность — внутри пакета, в перечисленных выше
   вложенных конструкциях.

Таким образом, тезис "SHOW_REPORT недостаточно детально репортит эти 20%"
**в широком смысле подтверждается**, но правильная формулировка ценности
инструмента — не "обнаружение того, что ora2pg не видит", а **"диагностика
того, что конкретно ora2pg либо (а) полностью пропускает без
предупреждения (COMPOUND TRIGGER), либо (б) недооценивает по стоимости
из-за собственных багов парсинга (PRAGMA в пакетах), либо (в) обезличивает
до потери актуальности (DBMS_*/UTL_*), либо (г) молча конвертирует
потенциально некорректно без флага риска (CONNECT BY)"**.

## Рекомендация: с чего начинать Задачу 1 (детектор packages)

С учётом находок выше, приоритет для Задачи 1 стоит скорректировать:

1. **Не начинать с "детектор наличия CREATE PACKAGE"** — это, как показано
   выше, не проблема сама по себе, у ora2pg с этим всё в порядке.
2. **Начать с детектора PRAGMA AUTONOMOUS_TRANSACTION *внутри тел пакетов*
   (PACKAGE BODY)** — это узкая, максимально конкретная, экспериментально
   подтверждённая и легко объяснимая (в т.ч. заказчику/архитектору) находка:
   мы можем прямо процитировать конкретный баг ora2pg (declare/code split в
   `_lookup_function`) и показать, что `SHOW_REPORT` для этого случая либо
   не даёт числа вообще, либо даёт заниженное. Практическая реализация
   детектора для Задачи 1: парсить `CREATE OR REPLACE PACKAGE BODY`,
   находить границы каждой функции/процедуры (`FUNCTION|PROCEDURE ... IS/AS
   ... BEGIN ... END`), искать `PRAGMA\s+AUTONOMOUS_TRANSACTION` в
   декларативной части (между `IS/AS` и `BEGIN`), и для каждого найденного
   вхождения формировать отдельную запись отчёта с: (а) именем
   пакета.функции, (б) точным фрагментом кода, (в) человекочитаемым
   объяснением "ora2pg перенесёт это через dblink-обёртку — требуется
   включить extension dblink и вручную задать connection string; если в
   контуре недопустимы кросс-соединения между процедурами/сетевые
   зависимости — нужна другая стратегия (например, отдельная
   autonomous-transaction-таблица + fire-and-forget через `pg_notify`, либо
   ручной рефакторинг)", (г) сложность по шкале (не просто "вес 3", а с
   учётом типа операции — commit внутри цикла явно сложнее, чем разовый
   commit).
3. Затем — **детектор COMPOUND TRIGGER** (второй по приоритету): максимально
   дёшево реализовать (искать `COMPOUND TRIGGER` как токен в DDL триггера —
   этого пока не делает вообще никто в пайплайне), максимально высокая
   ценность (полный, тихий провал у ora2pg).
4. Детектор для `DBMS_*/UTL_*` имеет смысл делать не как "обнаружение
   факта использования" (это уже делает `SHOW_REPORT`, пусть и обезличенно),
   а сразу как **классификатор конкретных функций** с обращением к
   собственному словарю "есть замена у ora2pg / нет замены / есть замена
   через orafce" — тогда он реально добавляет то, чего в `SHOW_REPORT` нет.
5. Детектор `CONNECT BY` — низкий приоритет для MVP (ora2pg сам неплохо его
   считает), но если делать — фокус не на "обнаружении", а на
   **валидации результата конвертации** (проверять сгенерированный
   `WITH RECURSIVE` на использование необъявленных алиасов вроде `LEVEL`
   вместо колонки глубины — это, по сути, отдельный класс задачи: линтинг
   вывода ora2pg, а не анализ входа).

ora2pg (`darold/ora2pg`, commit `cc2c434f`, `VERSION=25.0`) клонировался
вне этого репозитория и не включён в коммит; для повтора:

```sh
git clone https://github.com/darold/ora2pg.git
apt-get install -y libdbi-perl   # единственная недостающая Perl-зависимость
mkdir -p /etc/ora2pg && touch /etc/ora2pg/ora2pg.conf
PERL5LIB=ora2pg/lib perl ora2pg/scripts/ora2pg \
  -t PACKAGE -i docs/research/samples/logger.pkb \
  --estimate_cost -o out.sql -b /tmp/out
```
