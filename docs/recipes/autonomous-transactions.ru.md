# Автономные транзакции

Покрывает: GAP-001 (`autonomous_tx`).

## Проблема

`PRAGMA AUTONOMOUS_TRANSACTION` выполняет подпрограмму в собственной
транзакции: то, что она закоммитила, остаётся, даже если вызывающий код
откатится. Внутри одной сессии PostgreSQL такого не умеет. `ora2pg` эту
прагму конвертирует, по умолчанию в обёртку через `dblink`: подпрограмма
становится `<имя>_atx`, а прокси вызывает её через второе соединение.
GAP-001 в том, что `--estimate_cost` для подпрограммы внутри тела пакета
ничего за это не начисляет, хотя на каждый вызов появляются расширение,
строка подключения и сетевой обмен.

Так что работа здесь - решение по каждой подпрограмме, а не исправление
синтаксиса. Сначала выясните, *зачем* каждая из них автономная;
большинство попадает в один из трёх случаев ниже.

## Случай 1: журнал, который должен пережить откат

Самая частая причина: записать строку в журнал ошибок и дать вызывающему
коду откатиться. В PostgreSQL на это два ответа.

**Если журнал может идти в лог сервера**, конвертировать нечего:
`RAISE LOG` не транзакционен.

```sql
CREATE PROCEDURE log_event(p_message text)
LANGUAGE plpgsql
AS $$
BEGIN
    RAISE LOG 'app: %', p_message;
END;
$$;
```

**Если журнал должен быть строкой таблицы**, ему нужно своё соединение -
ровно это и делает обёртка `ora2pg`. Вручную это коротко:

```pgsql
CREATE TABLE app_log (
    logged_at timestamptz NOT NULL DEFAULT clock_timestamp(),
    message   text NOT NULL
);
```

```sql
CREATE EXTENSION IF NOT EXISTS dblink;

CREATE PROCEDURE log_autonomous(p_message text)
LANGUAGE plpgsql
AS $$
BEGIN
    -- Второе соединение к той же базе коммитит само по себе.
    -- Допишите user/password (или используйте ~/.pgpass) под свою установку.
    PERFORM dblink_exec(
        'dbname=' || current_database(),
        format('INSERT INTO app_log (message) VALUES (%L)', p_message)
    );
END;
$$;
```

Это проверено на настоящем сервере: обычная вставка откатывается вместе с
упавшим блоком, автономная - нет.

```sql
CREATE TABLE app_log_plain (message text);

-- Второе соединение видит только закоммиченные таблицы. В вашей базе
-- app_log уже есть; проверка создаёт её тем же способом.
SELECT dblink_exec(
    'dbname=' || current_database(),
    'CREATE TABLE IF NOT EXISTS app_log (
         logged_at timestamptz NOT NULL DEFAULT clock_timestamp(),
         message   text NOT NULL)'
);

DO $$
BEGIN
    BEGIN
        INSERT INTO app_log_plain VALUES ('plain');
        CALL log_autonomous('autonomous');
        RAISE EXCEPTION 'business error';
    EXCEPTION WHEN raise_exception THEN
        NULL;  -- здесь откатывается собственная работа блока
    END;
    ASSERT (SELECT count(*) FROM app_log_plain) = 0;
    ASSERT (SELECT count(*) FROM app_log WHERE message = 'autonomous') = 1;
END $$;
```

Что нужно знать, прежде чем выбрать вариант с таблицей:

- Каждый вызов открывает соединение. Журналирование внутри горячего цикла
  станет медленным; пишите один раз на ошибку или собирайте сообщения и
  записывайте их одним вызовом.
- Пользователь без прав суперпользователя может работать с `dblink` только
  с паролем в строке подключения (или через сопоставление пользователей в
  духе `postgres_fdw`). Не держите пароль в коде: директива `DBLINK_CONN`
  в `ora2pg.conf` задаёт его один раз для сгенерированных обёрток.
- Второе соединение не видит незакоммиченных строк вызывающего кода - так
  же, как в Oracle.

## Случай 2: COMMIT внутри триггера или функции

Иногда код автономен только потому, что хочет сделать `COMMIT` там, где
Oracle иначе не позволяет. В PostgreSQL:

- **Процедура**, вызванная через `CALL` вне явного блока транзакции, может
  сама делать `COMMIT` и `ROLLBACK`. Если автономная подпрограмма была
  самостоятельной единицей работы, сделайте её процедурой и уберите прагму.
- **Функция** или **триггер** коммитить не могут. Если это действительно
  необходимо, это случай 1 (второе соединение). Часто не нужно: коммит
  стоял, чтобы раньше освободить блокировки, а в PostgreSQL это сделает
  коммит вызывающего кода.

## Случай 3: фоновая задача

Код, который запускает работу, обязанную пережить вызывающего (отправить
письмо, пересчитать сводку), - это очередь, а не транзакция. Вставьте
строку в таблицу заданий в транзакции вызывающего кода и дайте обработчику
выполнить её после коммита, или используйте расширение, сделанное для
этого (`pg_cron` для расписаний, `pg_background` для разовых фоновых
команд).

## Со стороны ora2pg

- `AUTONOMOUS_TRANSACTION 1` (по умолчанию) - `ora2pg` генерирует обёртку
  через `dblink`; `0` - подпрограмма выгружается как обычная, без прагмы,
  это то, что нужно для случая 2.
- `PG_BACKGROUND 1` - вместо обёртки через `dblink` генерируется обёртка
  через `pg_background`. Это расширение не входит в сам PostgreSQL;
  сначала установите его на сервер.
- Заложите это в план сами: `--estimate_cost` этого не делает для
  подпрограммы в теле пакета (GAP-001).
